# Eclair (and other single-port services) stay on a random port forever if 9735 was taken at install — reinstall to fix

## Symptom

Eclair's Peer interface shows an external port that is not 9735 — for example:

```
$ start-cli package host eclair binding peer list
+---------------+---------+---------------+-------------------+
| INTERNAL PORT | ENABLED | EXTERNAL PORT | EXTERNAL SSL PORT |
+---------------+---------+---------------+-------------------+
| 9735          | true    | 49405         | N/A               |
+---------------+---------+---------------+-------------------+
```

The node's URI is Tor-only — no clearnet address is announced — even though a published port for 9735 exists and no error or warning appears anywhere. Restarting Eclair, rebooting the server, uninstalling whatever else was using 9735, and removing and re-adding the StartTunnel port forward all make no difference: the external port stays the same.

## Affects

Any service on StartOS whose interface asks for a specific external port (`preferredExternalPort`) and was refused it because another service already held that port at the time the interface was first created — most commonly a second Lightning node installed after a first one already holds 9735 externally. Once refused, the assignment never changes on its own, on any StartOS 0.4.0.x release, no matter how many times the service or server is restarted. A service that can advertise a different port than it listens on (c-lightning is an example) is only inconvenienced by this; a service like Eclair that cannot is left completely unreachable over clearnet with no visible warning.

## Cause

StartOS decides a binding's external port only once, when the interface is first created. If the preferred port is free at that moment it is used; if not, the service is handed a random free ("ephemeral") port and keeps it permanently — every later start re-applies the old assignment rather than re-checking whether the preferred port has since become free. Nothing in StartOS compares the assigned port against the preferred one or reports a mismatch, so neither the operator nor the package is ever told the request was refused.

## Remedy

There is no setting that moves an existing binding's external port on 0.4.0.1 or 0.4.0.2. The affected package must be uninstalled (with its data backed up first) and reinstalled after confirming the wanted port is free — a fresh interface goes through the code path that honours the preferred port. For Eclair specifically, update to eclair-startos 0.14.3:0 or later, which additionally falls back to fixed alternate ports (19735, then 29735) if 9735 is still unavailable at install — check its own documentation before moving the listener if a Tor address is already attached, since moving it drops that .onion and a new one must be generated.

## Do not

- Restarting the service, rebooting StartOS, or removing and re-adding a StartTunnel forward — none of these re-evaluate the binding; only a fresh interface (via reinstall) does.
- Uninstalling the other service holding the port first and then just restarting the affected one — freeing the port does not make the parked binding reclaim it.

## Notes

- `start-cli package host <pkg> binding <host> list` is the way to see the actual assigned external port versus what was requested; there is no UI indicator for this mismatch.
- A stopped or disabled service still holds its assigned external port — the service occupying a contested port is not necessarily the one currently running.
- Tracked upstream as Start9Labs/start-technologies#3990, with a broader fix (an operator command to reclaim a preferred port, and a matched internal/external bind option for the SDK) proposed but not yet merged.
