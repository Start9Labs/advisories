# StartOS: adding a public domain for Electrum, clnrest, turns or LND REST silently fails, address refuses every connection — fix ships in 0.4.0.2

## Symptom

Adding a public (clearnet) domain for an interface that StartOS serves TLS for on a port other than 443 — for example Electrum on `50002`, clnrest on `3010`, `turns` on `5349`, or LND REST on `8080` — passes every check with no warning. The setup modal does not reopen with an error; you just see a new row reading `Let's Encrypt`. Afterwards the address refuses every connection with a fatal TLS error, `unrecognized_name`.

## Affects

Anyone adding a public domain for a service or interface whose certificate is served on a non-443 port. Public domains for interfaces served directly on 443 (the common case, e.g. most web UIs) are not affected.

## Cause

Adding a public domain runs DNS, IPv4 port-forwarding and IPv6 firewall checks against the interface's own external port. Let's Encrypt's TLS-ALPN-01 challenge, however, is always validated at `<domain>:443` regardless of which port the interface is actually served on, so none of the existing checks actually tested the one thing that determines whether the domain will work.

## Remedy

Update to StartOS 0.4.0.2, which adds a dedicated check of port 443 (IPv4 and, where applicable, IPv6) whenever the domain needs a certificate authority and is served elsewhere, and opens the required port 443 firewall/forwarding rule automatically. The setup modal now shows a Certificate Authority section reflecting this check, and Port Forwards lists the 443 rule alongside the interface's own so it can be opened on the router.

Until updating, avoid adding a public domain for an interface served on a non-443 port; if one was already added and is failing with `unrecognized_name`, remove and re-add it after updating to 0.4.0.2.

## Notes

Behaviour change to be aware of after the fix: dialling `https://<name>` with no port, for a domain published on a different port, is now refused outright rather than being proxied to the service — this is intentional and documented in the changelog.
