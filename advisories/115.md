# Public domain on Electrum, clnrest, turns, or LND REST can present a StartOS local certificate instead of Let's Encrypt — fixed in StartOS 0.4.0.2

## Symptom

After adding a public domain with Let's Encrypt to an interface that StartOS serves TLS for on a port other than 443 — for example Electrum on `50002`, clnrest on `3010`, `turns` on `5349`, or LND REST on `8080` — the UI says `Let's Encrypt`, but the endpoint can present a certificate issued by the StartOS Local CA instead. Clients that trust public certificate authorities but not the server's Local CA then reject the connection, even though the DNS and port checks passed.

## Affects

StartOS 0.4.0.1 users who select Let's Encrypt for a public domain on an interface where StartOS terminates TLS on a non-443 port. Interfaces served on 443 are not affected. A domain using the Local Root CA works for clients that trust that CA.

## Cause

Let's Encrypt validates its TLS-ALPN-01 challenge at `<domain>:443` regardless of which port the interface uses. StartOS associates the certificate request with the interface's own port but does not route the challenge arriving on port 443 to it, so the order cannot complete. The add-domain checks test the interface's port rather than the challenge port and can therefore pass without detecting the certificate problem.

## Remedy

Update to StartOS 0.4.0.2. It routes certificate challenges arriving on port 443 to domains served on other ports, checks that port when a domain is added, enabled, or retested, and lists its forwarding requirement alongside the interface's own port. On a router without automatic port forwarding, keep port 443 forwarded to the StartOS server as well as the interface's port.

Do not remove a non-443 public domain that already works and presents a valid public certificate; update before its next renewal. Until updating, the Local Root CA remains an option for clients on which the server's Root CA can be installed and trusted.
