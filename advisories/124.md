# Open WebUI: a shared folder collaborator with write access becomes read-only after reloading the page

## Symptom

A user given write access to a shared folder can open it from the sidebar and gets a normal folder page with a message box and folder menu. Reloading that page, or opening the folder's link directly (e.g. in a new tab), instead shows a read-only page: the message box, the folder menu and the folder icon button are all gone, and no chat can be started in the folder — even though their access has not changed. Nothing is logged on either side; both requests succeed.

## Affects

Anyone using a shared folder as a non-admin collaborator with write permission. Only reproduces on reload or by opening the folder's address directly; navigating in from the sidebar's Shared list works correctly. Admins are not affected.

## Cause

The folder page decides whether to show write controls from a permission field the sidebar's shared-folder listing supplies. On reload the page instead fetches the folder directly, and that response omits the permission field, so a collaborator with write access is read as read-only.

## Remedy

No fix has been released yet. A collaborator who loses write access after a reload should navigate back into the folder from the Shared list in the sidebar rather than reloading or reopening the folder's direct link; that restores the message box and folder menu.

## Notes

A pull request (#30317) proposing to include the caller's permission in the folder-fetch response, matching what the shared folder chats endpoint already returns, has been opened but not merged.
