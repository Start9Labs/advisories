# Core Lightning: dual-funded (v2) channel opens can be used to drain funds — disable experimental dual-fund

## Symptom

A peer opens a dual-funded channel, drains most or all of the node's liquidity, then goes offline. The channel's `funding_txid` cannot be found in the mempool or on a block explorer, but the same peer's node ID shows a different, real transaction on network graph explorers like Amboss. Attempting to force-close the channel leaves it in `AWAIT_UNILATERAL`. Logs show the channel cycling through `DUALOPEND_OPEN_INIT` → `DUALOPEND_AWAITING_LOCKIN`, then a `WIRE_TX_SIGNATURES` message arriving "after channel_ready... ignoring", followed by the subdaemon dying and the channel moving to `CHANNELD_NORMAL` anyway.

## Affects

Core Lightning nodes running 26.06.7 with `--experimental-dual-fund` enabled, which accept dual-funded (v2) channel opens from peers. Nodes that have not enabled this experimental option are not affected.

## Remedy

Disable the `experimental-dual-fund` option until Start9 or the Core Lightning project advises otherwise. This is an early mitigation while the underlying issue is investigated; there is not yet a fixed version to update to.

## Do not

- Do not assume force-closing recovers funds — affected users report the channel gets stuck in `AWAIT_UNILATERAL` without resolving the loss.
- Do not treat a mismatched or missing `funding_txid` as a local sync problem — it appears tied to this dual-fund issue, not to bitcoind or Core Lightning's chain sync.

## Notes

Investigation is early and this issue is still open; only the dual-fund mitigation is confirmed so far. Multiple independent reports of drained channels exist as of this writing. Check back for a fixed version once one is announced.
