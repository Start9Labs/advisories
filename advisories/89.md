# Nextcloud Desktop repeatedly shows "Network error" then reconnects on its own — proxy issue, safe to ignore

## Symptom

The Nextcloud Desktop client (Windows or Linux) periodically flips from "Connected" to **"Network error"** and then recovers on its own a few seconds later, with no user action needed and no lasting effect on sync. Client debug logs show `QNetworkReply::RemoteHostClosedError "Connection closed"` on the periodic status check, followed by `AccountState state change: "Connected" -> "Network error"` and then a normal reconnect. The Nextcloud service log shows paired `408` entries around the same time:

```
10.0.[redacted] - - "-" 408 0 "-" "-"
10.0.[redacted] - - "-" 408 0 "-" "-"
```

followed about 10 seconds later by a fresh burst of normal requests (`/index.php/204`, `/status.php`, `PROPFIND ...`) as the client reconnects. The web interface (browser) does not show this because browsers silently retry.

## Affects

Anyone accessing a service — most visibly Nextcloud — through StartOS's reverse proxy over an `http`/`https` address (`.local`, LAN IP, router domain, or StartTunnel) using a client that keeps a persistent connection open, such as Nextcloud Desktop's sync client. It does not affect `.onion` addresses, which bypass this proxy path, or plain web-browser use, which masks the aborts by retrying.

## Cause

StartOS's reverse proxy dials one upstream connection per client connection and never re-dials it. When the backend (e.g. Apache in the Nextcloud container) closes that connection after its own keep-alive timeout — 5 seconds by default — the proxy does not notice and keeps the client's side of the connection open for up to 60 seconds. If the client tries to reuse that connection in the meantime, the proxy aborts it with no response, which the client reports as a connection reset.

## Remedy

This is a known proxy behavior, not a fault in Nextcloud or the client. It causes no data loss and no action is needed — the client reconnects automatically within a few seconds. The nextcloud-startos package has already been updated to raise the backend's own keep-alive timeout above the proxy's window, which reduces how often this is hit; update to the latest available Nextcloud package version for that mitigation. A full fix in StartOS's proxy (so backend keep-alive expiry is never visible to clients) is a known issue but has not shipped.

## Do not

- Do not treat this as a sign of a failing network, disk, or Nextcloud install — sync itself keeps working and no data is at risk.
- Do not re-enter credentials or reconfigure the client — this does not fix or prevent the flap.

## Notes

- Reported through Nextcloud specifically, but the underlying proxy behavior affects any service reached over an `http`/`https`-preset address through a persistent-connection client (sync tools, API pollers); other packages may see the same intermittent disconnect-and-recover pattern.
- The same StartOS issue also produces harmless `408` log-line pairs in the backend's access log from the client's speculative/idle connections; these do not indicate an attack or misconfiguration.
