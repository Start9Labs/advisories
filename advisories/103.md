# Jellyfin: upgrading to 12.1 can corrupt jellyfin.db if anything else reads it before a restart

## Symptom

Some hours after updating to Jellyfin 12.1, web login stops working (infinite loader), `GET /users/public` returns 500, and `/socket` fails with "Token is required". The log fills with:

```
Microsoft.Data.Sqlite.SqliteException (0x80004005): SQLite Error 11: 'database disk image is malformed'.
```

`PRAGMA integrity_check` on the database shows zero-filled pages and `wrong # of entries` in the `Users`, `Devices` and `UserData` tables and their indexes.

## Affects

Anyone updating Jellyfin to 12.1 (the migration runs once, on the 12.0→12.1 transition) whose server, or anything else on the same host, reads `jellyfin.db` directly while Jellyfin keeps running — for example a backup script or stats tool that runs `sqlite3 jellyfin.db .dump` or opens the file read-only. It does not affect a server that never has anything else opening `jellyfin.db` directly, and it does not recur on later restarts once the update has completed and no further migration runs.

## Cause

12.1's migration backup (`MigrationBackupFast`) opens a pooled SQLite connection to checkpoint the WAL, then closes it with `File.Copy`. Closing that file descriptor releases every POSIX advisory lock the process holds on `jellyfin.db`, including the SHARED lock Jellyfin's own connections rely on, but SQLite's internal bookkeeping still believes the lock is held, so it is never retaken. From then until Jellyfin is restarted, any external process that opens and closes the database believes it is the last connection, checkpoints, and deletes the live `jellyfin.db-wal` and `jellyfin.db-shm` out from under the running server, corrupting the database on the next write.

## Remedy

This is confirmed upstream and reproduced deterministically; there is no fix in 12.1 or earlier. Until a fixed release ships, avoid any read of `jellyfin.db` from outside Jellyfin (backup scripts, stats tools, manual `sqlite3` access) between a Jellyfin update and the next restart of the service. A plain restart of the Jellyfin service after the update completes clears the unlocked state.

If corruption has already happened (`SQLite Error 11: 'database disk image is malformed'`, web login broken), there is no automatic repair. A row-level salvage script exists that copies the priority tables (users, playstates, API keys, people, providers) into a fresh database, after which libraries must be re-created and rescanned; see the linked issue's discussion for the script.

## Do not

- Do not assume restoring a StartOS backup avoids this — the corruption happens after the update completes and can affect a database backed up mid-corruption too; check for `SQLite Error 11` in the log first.

## Notes

- Only surfaces on the 12.0→12.1 migration itself; a server already on 12.1, or one that never runs anything that reads `jellyfin.db` externally, will not hit this.
- The salvage script referenced in the discussion was originally posted against a different, unrelated 10.x issue and cross-linked here for 12.x upgraders.
