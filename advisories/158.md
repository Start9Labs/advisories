# Open WebUI: Korean and Japanese text file uploads are garbled as Chinese characters

## Symptom

A Korean (EUC-KR) or Japanese (Shift-JIS) text file is uploaded — to a chat or a knowledge base — and the stored text comes out as garbled Chinese-looking characters instead of the original content. Retrieval, knowledge base answers and anything the model is given from that file all work from this corrupted text, not what was in the file.

## Affects

Anyone uploading Korean or Japanese plain-text files on Open WebUI 0.10.0 or later. Chinese, EUC-JP, UTF-8 and Western-encoded files are unaffected. A short file or snippet containing only a few Chinese characters (e.g. a short label or one-line comment) can still be misread as Korean even after the fix.

## Cause

Encoding detection tries chardet's guess before a fixed try-order of GB18030, Big5, EUC-KR, EUC-JP, and GB18030 decodes almost any double-byte text without raising an error. The guess-to-codec map was written for chardet 5; since chardet 7 (introduced in v0.10.0) reports Korean text as CP949 and Japanese text as cp932/SHIFT_JIS, which the old map did not recognize, so these files fell through to GB18030 and decoded as Chinese.

## Remedy

This is fixed upstream, but the fix has not yet reached a released version of Open WebUI on StartOS — there is no release date yet. Once it is available, Korean and Japanese text uploads will decode correctly again. In the meantime, avoid relying on Korean or Japanese text uploads to knowledge bases or chats; if a file has already been uploaded and answers look wrong, re-upload it once the fix is available rather than trying to repair the stored text.

## Notes

Very short Chinese text (a short label or one-line comment) can still be misdetected as Korean after the fix; this is a known trade-off, not a new bug.
