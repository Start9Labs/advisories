# LND initial graph sync stalls indefinitely against pruned bitcoind

## Symptom

A freshly installed LND, syncing its channel graph for the first time against a pruned bitcoind, gets stuck on "Syncing to graph" and never completes. Peers disconnect repeatedly on ping/pong timeouts, `lncli getinfo` stops responding within 30 seconds and StartOS's sync-progress check kills it, and the node stays stuck in this loop indefinitely. Enabling pprof shows hundreds to thousands of goroutines piling up in `discovery.AuthenticatedGossiper.validateFundingTransaction` and `blockcache.BlockCache.GetBlock`, blocked on requests to `BitcoindConn.GetBlock`.

## Affects

Fresh LND installs (empty graph) run against a pruned bitcoind, where LND must validate tens of thousands of historical channel announcements by fetching old blocks on demand through btc-rpc-proxy over Tor. Does not affect nodes with an already-synced graph, or LND run against a non-pruned (archival) bitcoind.

## Cause

With a pruned bitcoind, LND fetches historical blocks for gossip validation on demand via btc-rpc-proxy's P2P fallback. During initial graph sync this generates thousands of concurrent block-fetch requests over Tor, which saturates the RPC queue and blocks LND's main event loop, causing `lncli getinfo` to time out and StartOS to kill the process.

## Remedy

Set `routing.assumechanvalid=true` in LND's configuration. This skips historical funding-transaction validation during gossip sync (the same default Neutrino uses for the same reason) and lets graph sync complete normally instead of stalling.

## Do not

- Do not treat this as a bitcoind or Tor connectivity problem — bitcoind and the proxy are working as designed; the bottleneck is LND's validation of historical blocks during gossip sync.

## Notes

- `assumechanvalid` is not currently exposed as a toggle in the LND service UI; it must be added to LND's configuration directly.
- The reporter also noted that when StartOS's sync-progress check SIGKILLs a stalled `lncli getinfo`, the inner `lncli` process can be left running as an orphan holding sockets open; this is a separate, unconfirmed issue and not part of this advisory.
