# Nextcloud (Legacy) and other 0.3.x packages with a certificate volume fail to start with `unknown hostname` on a server with a WAN IP

## Symptom

A legacy (0.3.x) package that declares a `certificate` volume — Nextcloud (Legacy) is the reported case — fails to start, going to Stopped immediately with no other activity. The log shows only:

```
start failed Error: Not Found: unknown hostname: 64.23.[redacted]
   0: unknown hostname: 64.23.[redacted]
Location: shared-libs/crates/start-core/src/service/effects/net/ssl.rs:50
…@get-ssl-certificate
```

or, on the OS log:

```
2026-09-05T14:45:02.826681Z ERROR start_core::error: Unknown Error: Error: Not Found: unknown hostname: 98.97.[redacted]
```

The hostname named in the error is the server's own WAN IP (the router's public IP, or a StartTunnel gateway's WAN IP) — not anything the customer configured. Every start attempt repeats it.

## Affects

Servers whose gateway reports a WAN IP — a router with a public IP, or a StartTunnel gateway — running a 0.3.x package that uses a `certificate` volume (e.g. Nextcloud Legacy). Commonly hit right after upgrading from StartOS 0.3.5.1 to 0.4.x, when the legacy service is started for the first time under the new OS. Packages without a `certificate` volume, and packages already migrated to 0.4.x-native, are unaffected.

## Cause

The 0.3.x compatibility runtime asks for a TLS certificate covering every address the host reports as available, including the gateway's WAN IP — an address that is not eligible for a certificate. The certificate service rejects that IP as an unknown hostname, and the compat runtime aborts the start instead of filtering it out.

## Remedy

No fix has shipped yet. Tell the customer this is a known bug, currently being worked; there is no setting or workaround that lets the legacy package start while a WAN IP is present on the gateway. If the service can be migrated off the legacy 0.3.x package to its current StartOS-native version, that avoids the problem entirely.

## Notes

Reported against StartOS 0.4.0.1 and reproduced on current master; no fix version exists yet, so none is given here.
