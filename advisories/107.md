# Restoring a backup from arm64 to an x86_64 server (or vice versa) fails with `file images/x86_64/main.squashfs missing from archive`

## Symptom

Restoring a service — or a full-server restore — from a backup made on one CPU architecture onto a server of the other architecture fails almost immediately with:

```
RPC Error: S9PK Parsing Error
file images/x86_64/main.squashfs missing from archive
```

(or the equivalent `aarch64` filename, if restoring in the other direction). Trying to work around it by installing the service fresh from the marketplace first, to get the correct-architecture image in place, and then restoring on top fails too, with:

```
Unavailable. Service is already installed
```

Full-server "Restore from Backup" fails the same way, within a minute or two of starting.

## Affects

Anyone restoring a StartOS backup (V2, native format) onto a server whose CPU architecture differs from the one the backup was made on — for example moving from an arm64 device (Raspberry Pi, CM3588, etc.) to an x86_64 machine, or the reverse. Restoring on matching-architecture hardware is unaffected.

## Cause

The backed-up `.s9pk` only contains the image for the architecture it was built/run on. StartOS's image-emulation fallback (`emulateMissingAs`) is hardcoded to look for an x86_64 image regardless of which architecture is actually missing, so it never finds the arm64 image sitting in the archive and aborts instead of emulating it.

## Remedy

There is no update or setting that avoids this on 0.4.0.1. A maintainer has confirmed the cause and proposed a fix (replacing `emulateMissingAs` with an architecture-agnostic `emulateMissing` flag), but it has not merged or shipped yet. Until a fixed version ships, cross-architecture restore is not supported — restore backups only onto a server matching the architecture they were taken on. There is no supported workaround for migrating a backup across architectures at this time.

## Do not

- Do not suggest installing the service from the marketplace first and then restoring — this fails with `Unavailable. Service is already installed` rather than helping.

## Notes

Reported as originating from a same-architecture-only environment historically; both StartOS 0.4.0 architectures ship signed images, so this can be hit whenever hardware is changed as part of a migration, not just by unusual configurations.
