# Discourse: uploading more than 10 files at once silently drops some — fixed, arriving in an upcoming release

## Symptom

Dragging a batch of files (for example, eleven images) into the composer or chat results in some files failing to upload, with no useful error — just "there was an error uploading" — and the failure discards other files still in progress in the same batch.

## Affects

Ordinary (non-staff) users uploading more than `max_uploads_per_minute` (10 by default) files within a minute, or otherwise triggering the upload rate limiter, on the default upload path (`enable_direct_s3_uploads` off). Staff accounts are exempt from this rate limit and will not reproduce it, which is why admins investigating a report often cannot.

## Cause

The rate limit response (HTTP 429) was not handled: the client's error display only recognized 0, 413 and 422, so a rate-limited upload showed a generic error. Worse, the error handling reset the entire uploader, which cancels every other file still uploading in the same batch, so one rate-limited file took down its siblings. Retries were also disabled, and S3 multipart uploads had additional signing and completion bugs that could discard a file whose data had already reached S3.

## Remedy

This is fixed upstream (discourse/discourse#43374, merged). The fix has not shipped in a Discourse release yet; when it does, updating to that version resolves it. In the meantime, uploading files in smaller batches (10 or fewer per minute) avoids triggering the rate limiter.

## Notes

No release has been named yet for this fix; update the advisory once one is confirmed.
