# Nextcloud (and other migrated services): a service update right after upgrading from 0.3.5.x can leave it stuck, with no rollback — reboot first

## Symptom

After upgrading StartOS from 0.3.5.x to 0.4.0.x, updating a package (for example Nextcloud) fails during its init/migration step. Unlike a normal failed update, the service is not rolled back to its previous working state — its data is left at whatever the failed update wrote, and every later attempt starts from that new, broken point. Trying to install the version the error message suggests going back to fails with its own migration error (e.g. `cannot migrate from 34.0.4:0 to 33.0.8:3`), and the previous (Legacy) version of the package can no longer start either. Nothing in the log mentions a rollback being skipped.

## Affects

Any service updated for the first time after upgrading StartOS from a 0.3.5.x release to 0.4.0.x, if that update is attempted before the server has rebooted since the OS upgrade. It does not affect services updated after a reboot, or servers that were never on 0.3.5.x.

## Cause

Volume roots carried over from 0.3.5.x are plain directories, not the btrfs subvolumes StartOS's update rollback relies on for a snapshot. The conversion to subvolumes only runs on boot, before packages are reinstalled — so on the very first boot after the 0.4.0 upgrade, no packages exist yet to convert, and the conversion is deferred to the next boot. If a service is updated before that next boot happens, its rollback snapshot silently fails (returns "no backup taken" with no warning logged), so a failed update cannot be undone.

## Remedy

Reboot the server once after upgrading StartOS from 0.3.5.x to 0.4.0.x, and before updating any service for the first time. This lets StartOS convert volume roots to the format its update rollback needs, so a failed update rolls back normally instead of leaving the service stuck.

If a service is already stuck in this state (update failed, old version won't start, suggested downgrade also fails), this is a data repair a Start9 staffer needs to help with directly — it is not something reapplying the update or downgrading further will fix on its own.

## Do not

- Retry the same update or try the version-downgrade the error message suggests — the volume is left at the failed migration's data version, so both routes fail with further migration errors instead of recovering it.

## Notes

Reported against StartOS 0.4.0.1; not yet fixed as of this report. No version fixes this yet — the difference from advisories #12/#20 is that this affects the *first service update* after the OS migration specifically, and leaves no rollback rather than a failed/missing migration.
