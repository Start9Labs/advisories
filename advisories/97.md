# StartOS: all containers lose external DNS lookups for minutes after a network blip — fix merged, arriving in a future update

## Symptom

After a WAN outage/recovery, tunnel churn, or a DHCP renewal, services inside containers suddenly can't resolve external hostnames at all — errors like `getaddrinfo: Temporary failure in name resolution`, `lookup api.getalby.com on 10.0.[redacted]:53: i/o timeout`, or `Could not resolve host: github.com` inside the container, while the StartOS host itself keeps working normally. It comes and goes in repeated bursts roughly every 11 seconds for anywhere from a few minutes up to half an hour or more, then clears on its own. Restarting or reinstalling the affected service does not help. It looks like a per-service networking bug, but it hits every container on the box at once during the episode.

## Affects

Any StartOS server, after a network event that disrupts or changes upstream DNS (WAN outage/recovery, StartTunnel outbound-gateway switch, DHCP renewal) combined with ongoing external DNS queries from containers. Internal `.startos` lookups for currently-running services are unaffected. The host's own DNS resolution is unaffected (it has a fallback resolver); only containers, which have a single nameserver, are hit.

## Cause

startd's DNS forwarder holds a read lock across each upstream forward (up to 30s) while the task that installs new upstream servers waits at most 10s for the write lock, then retries from the back of the queue. Under sustained query load against slow or dead upstreams, the writer starves indefinitely, blocking all new external lookups box-wide — including the very update that would fix the upstream list.

## Remedy

This is fixed in a merged change and will ship in a future StartOS update; no version is set yet. Until then, if a customer is hitting repeated DNS outages after network changes, setting static upstream DNS servers while DNS is currently healthy reduces exposure to this failure (it does not help mid-episode, and StartTunnel or router DNS changes can still trigger it).

## Do not

- Don't have them chase this as a per-service bug — restarting or reinstalling the affected service does not help, since the outage is in the shared DNS forwarder, not the service.

## Notes

Confirmed by a maintainer, who opened and merged a fix (#3507) that removes the read-guard-across-forward pattern, lowers the forward timeout, and removes the write-lock starvation entirely. A related but separate WAN-IP-probe failure (both echo providers failing at once) was called out by the reporter as likely a different issue and is not part of this advisory.
