# NextExplorer: password-protected shares open for other signed-in accounts without asking for the password

## Symptom

A folder shared with a password is supposed to require that password before anyone can open it. Instead, any other account already signed in to the same NextExplorer instance can open the share directly — by following the link or by going straight to a folder inside it — without ever being prompted for the password. The share's owner, meanwhile, is asked for their own share's password. A visitor who is not signed in and has already typed the password correctly may also be asked again on reload.

## Affects

Anyone using NextExplorer's password-protected sharing feature on an instance with more than one account. The owner of the share and anonymous (not signed-in) visitors are prompted correctly; the gap is specific to other signed-in accounts on the same instance.

## Cause

The access check only tested whether a session existed (a user or a guest), not whether that particular account had supplied the share's password, so any authenticated account was treated as already verified.

## Remedy

This is fixed upstream, but the fix has not yet reached the Start9 Registry — there is no released version containing it yet. Until it does, treat password-protected shares as visible to any other account on the instance, and avoid relying on a share's password to keep other users of the same NextExplorer instance out of it. Once a release containing the fix is available, updating to it restores the intended behavior; changing a share's password after updating will also revoke any guest sessions the old password had granted.

## Notes

- Also fixed in the same change: changing or setting a share's password now revokes guest sessions it had granted; previously those guest sessions (which last a day) kept working even after the password changed.
- Does not affect anonymous, signed-out visitors, who are correctly prompted for the share password, or the share's owner.
