# Jellyfin update from 10.11.11 to 12.0 fails with "SQLite Error 19: 'FOREIGN KEY constraint failed'" — fixed in 12.1

## Symptom

During the update, startup fails on one of the 12.0 migrations — `RemoveOrphanedUserPermissionsAndPreferences`, `FixIncorrectOwnerIdRelationships` or `ConsolidateLocalizedUserViews` — with:

```
[FTL] InternalDatabaseMigration: Error: "SQLite Error 19: 'FOREIGN KEY constraint failed'."
```

(`InternalCodeMigration` for the latter two.) The migration rolls back, `Main: Error while starting server` is logged, and the server never becomes available — it restarts and repeats the same failure indefinitely.

## Affects

Users updating Jellyfin from 10.11.11 to 12.0 whose SQLite database holds rows a migration's foreign-key check rejects — for `RemoveOrphanedUserPermissionsAndPreferences`, `Preferences` or `Permissions` rows referencing a user that was previously deleted. Reported on both Docker and native apt/LXC installs. Databases without such rows are not affected.

## Cause

`RemoveOrphanedUserPermissionsAndPreferences` deletes rows with a NULL `UserId` before making `UserId` non-nullable, but does not delete rows whose `UserId` is non-NULL yet does not match any existing user. The subsequent table rebuild enforces the foreign key and fails on those orphaned rows. `FixIncorrectOwnerIdRelationships` and `ConsolidateLocalizedUserViews` fail the same way on inconsistent rows of their own.

## Remedy

Update to Jellyfin 12.1, which contains the fixes for all three migrations (jellyfin/jellyfin#17835, jellyfin/jellyfin#17873).

Already stuck on 12.0, restore the backup taken before the update and stay on 10.11.11 until 12.1 is available; the failed migration rolls back, so the database is unchanged and nothing is lost. If the failing migration is `RemoveOrphanedUserPermissionsAndPreferences`, the orphaned rows can be removed directly from the database (after taking a backup) so the migration completes:

```sql
DELETE FROM Preferences WHERE UserId NOT IN (SELECT Id FROM Users);
DELETE FROM Permissions WHERE UserId NOT IN (SELECT Id FROM Users);
```

Before deleting, confirm the rows are genuinely orphaned rather than differing from a valid user GUID by case or hyphenation, since `UserId` is stored as TEXT:

```sql
SELECT DISTINCT UserId FROM Preferences WHERE UserId NOT IN (SELECT Id FROM Users);
SELECT Id, Username FROM Users;
```

## Notes

- Editing the Jellyfin database directly requires a SQL client capable of opening the `jellyfin.db` file; StartOS does not provide one, so this needs an external tool applied to the file after it is retrieved from the service's data.
- The rollback behaves correctly: repeated failed attempts leave the database file unchanged, so no data is lost while diagnosing.
