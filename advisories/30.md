# Jellyfin: update to 12.0 fails with "SQLite Error 19: 'FOREIGN KEY constraint failed'" — fixed in 12.1

## Symptom

During the update, startup fails on one of the 12.0 migrations — `RemoveOrphanedUserPermissionsAndPreferences`, `FixIncorrectOwnerIdRelationships`, `ConsolidateLocalizedUserViews` or `ChangeOwnerIdToGuid` — with:

```
[FTL] InternalDatabaseMigration: Error: "SQLite Error 19: 'FOREIGN KEY constraint failed'."
```

(`InternalCodeMigration` for `FixIncorrectOwnerIdRelationships` and `ConsolidateLocalizedUserViews`.) The migration rolls back, `Main: Error while starting server` is logged, and the server never becomes available — it restarts and repeats the same failure indefinitely.

For `ChangeOwnerIdToGuid`, the process instead completes its normal shutdown/DB-optimize sequence after the fatal error and exits with code 0, so a restart-on-failure policy does not trigger — the service appears cleanly stopped rather than crashed, which can delay noticing the failure.

## Affects

Users updating Jellyfin from 10.11.x to 12.0 whose SQLite database holds rows a migration's foreign-key check rejects — for `RemoveOrphanedUserPermissionsAndPreferences`, `Preferences` or `Permissions` rows referencing a user that was previously deleted; for `ConsolidateLocalizedUserViews`, `AncestorIds` rows whose `ItemId` matches no `BaseItems` row (seen with the Live TV view), or other rows still referencing a stale user view before it is dropped. Also seen with self-referencing `ParentIds` rows, which fail the same foreign-key check during migration. For `ChangeOwnerIdToGuid`, `BaseItems.OwnerId` rows set to the sentinel `00000000-0000-0000-0000-000000000000` (seen on every `Person` cast/crew row in one long-lived library) or to a real GUID pointing at an item long removed from the library; also seen with pre-existing orphaned rows across `AncestorIds`, `AttachmentStreamInfos`, `BaseItemImageInfos`, `BaseItemProviders`, `Chapters`, `ItemValuesMap`, `KeyframeData`, `MediaStreamInfos`, `PeopleBaseItemMap` and `UserData`, and with `BaseItems.ParentId` self-references to already-deleted rows — none of which were enforced or surfaced under 10.x. Reported on both Docker and native apt/LXC installs. Databases without such rows are not affected.

## Cause

`RemoveOrphanedUserPermissionsAndPreferences` deletes rows with a NULL `UserId` before making `UserId` non-nullable, but does not delete rows whose `UserId` is non-NULL yet does not match any existing user. The subsequent table rebuild enforces the foreign key and fails on those orphaned rows. `FixIncorrectOwnerIdRelationships` and `ConsolidateLocalizedUserViews` fail the same way on inconsistent rows of their own, including self-referencing `ParentIds` rows and rows still referencing a stale user view before it is dropped. `ChangeOwnerIdToGuid` copies `BaseItems` into a temporary table under a schema that, as of the subsequent `AddForeignKeyToOwnerId` migration, enforces a foreign key on `OwnerId`; pre-12.0 schemas never enforced or constrained that column, so long-lived databases accumulate `OwnerId` sentinel values, stale references, and other orphaned rows across related tables that only surface as failures once the constraint is added.

## Remedy

Update to Jellyfin 12.1, which contains the fixes for all four migrations (jellyfin/jellyfin#17835, jellyfin/jellyfin#17873).

Already stuck on 12.0, restore the backup taken before the update and stay on 10.11.11 until 12.1 is available; the failed migration rolls back, so the database is unchanged and nothing is lost. If the failing migration is `RemoveOrphanedUserPermissionsAndPreferences`, the orphaned rows can be removed directly from the database (after taking a backup) so the migration completes:

```sql
DELETE FROM Preferences WHERE UserId NOT IN (SELECT Id FROM Users);
DELETE FROM Permissions WHERE UserId NOT IN (SELECT Id FROM Users);
```

Before deleting, confirm the rows are genuinely orphaned rather than differing from a valid user GUID by case or hyphenation, since `UserId` is stored as TEXT:

```sql
SELECT DISTINCT UserId FROM Preferences WHERE UserId NOT IN (SELECT Id FROM Users);
SELECT Id, Username FROM Users;
```

If the failing migration is `ChangeOwnerIdToGuid`, first run `REINDEX;` against the database and re-check with `PRAGMA foreign_key_check;` — a corrupted index can make valid references appear orphaned, and one user found `REINDEX;` alone resolved all but one violation. Only after that should any remaining orphaned rows be cleaned up (after taking a backup):

```sql
-- normalize case-mismatched-but-valid OwnerId references
UPDATE BaseItems
SET OwnerId = (SELECT b2.Id FROM BaseItems b2 WHERE LOWER(b2.Id) = LOWER(BaseItems.OwnerId))
WHERE OwnerId IS NOT NULL
  AND OwnerId NOT IN (SELECT Id FROM BaseItems)
  AND LOWER(OwnerId) IN (SELECT LOWER(Id) FROM BaseItems);

-- null out anything left that doesn't resolve (sentinel / corrupt / truly orphaned)
UPDATE BaseItems
SET OwnerId = NULL
WHERE OwnerId IS NOT NULL
  AND OwnerId NOT IN (SELECT Id FROM BaseItems);

-- detach BaseItems whose ParentId points at a deleted row
UPDATE BaseItems
SET ParentId = NULL
WHERE ParentId IS NOT NULL
  AND ParentId NOT IN (SELECT Id FROM BaseItems);

-- drop metadata for child rows whose parent BaseItems row is entirely gone
DELETE FROM AncestorIds
WHERE ItemId NOT IN (SELECT Id FROM BaseItems)
   OR ParentItemId NOT IN (SELECT Id FROM BaseItems);
DELETE FROM AttachmentStreamInfos WHERE ItemId NOT IN (SELECT Id FROM BaseItems);
DELETE FROM BaseItemImageInfos    WHERE ItemId NOT IN (SELECT Id FROM BaseItems);
DELETE FROM BaseItemProviders     WHERE ItemId NOT IN (SELECT Id FROM BaseItems);
DELETE FROM Chapters              WHERE ItemId NOT IN (SELECT Id FROM BaseItems);
DELETE FROM ItemValuesMap         WHERE ItemId NOT IN (SELECT Id FROM BaseItems);
DELETE FROM KeyframeData          WHERE ItemId NOT IN (SELECT Id FROM BaseItems);
DELETE FROM MediaStreamInfos      WHERE ItemId NOT IN (SELECT Id FROM BaseItems);
DELETE FROM PeopleBaseItemMap     WHERE ItemId NOT IN (SELECT Id FROM BaseItems);
DELETE FROM UserData               WHERE ItemId NOT IN (SELECT Id FROM BaseItems);
```

## Notes

- Editing the Jellyfin database directly requires a SQL client capable of opening the `jellyfin.db` file; StartOS does not provide one, so this needs an external tool applied to the file after it is retrieved from the service's data.
- The rollback behaves correctly: repeated failed attempts leave the database file unchanged, so no data is lost while diagnosing.
- Unconfirmed: because the `ChangeOwnerIdToGuid` failure can exit with code 0 rather than a nonzero code, process supervisors that only restart on failure may not restart the service or flag it as down; this may need to be checked for manually rather than relied on to surface via automatic restarts.
