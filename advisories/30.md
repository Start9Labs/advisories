# Jellyfin update from 10.11.11 to 12.0 fails with "SQLite Error 19: 'FOREIGN KEY constraint failed'"

## Symptom

During the update, startup fails on the migration `20260815063607_RemoveOrphanedUserPermissionsAndPreferences` with:

```
[FTL] InternalDatabaseMigration: Error: "SQLite Error 19: 'FOREIGN KEY constraint failed'."
```

The migration rolls back, `Main: Error while starting server` is logged, and the server never becomes available — it restarts and repeats the same failure indefinitely.

## Affects

Users updating Jellyfin from 10.11.11 to 12.0 whose SQLite database contains `Preferences` or `Permissions` rows referencing a user that was previously deleted. Reported on both Docker and native apt/LXC installs. Databases without orphaned rows referencing deleted users are not affected.

## Cause

The migration deletes rows with a NULL `UserId` before making `UserId` non-nullable, but does not delete rows whose `UserId` is non-NULL yet does not match any existing user. The subsequent table rebuild enforces the foreign key and fails on those orphaned rows.

## Remedy

Update to Jellyfin 12.1, which contains the fix (jellyfin/jellyfin#17835).

If already stuck on the failing migration on 12.0, the orphaned rows can be removed directly from the database (after taking a backup) so the migration completes:

```sql
DELETE FROM Preferences WHERE UserId NOT IN (SELECT Id FROM Users);
DELETE FROM Permissions WHERE UserId NOT IN (SELECT Id FROM Users);
```

Before deleting, confirm the rows are genuinely orphaned rather than differing from a valid user GUID by case or hyphenation, since `UserId` is stored as TEXT:

```sql
SELECT DISTINCT UserId FROM Preferences WHERE UserId NOT IN (SELECT Id FROM Users);
SELECT Id, Username FROM Users;
```

## Notes

- Editing the Jellyfin database directly requires a SQL client capable of opening the `jellyfin.db` file; StartOS does not provide one, so this needs an external tool applied to the file after it is retrieved from the service's data.
- The rollback behaves correctly: repeated failed attempts leave the database file unchanged, so no data is lost while diagnosing.
