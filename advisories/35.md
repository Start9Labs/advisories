# Selecting a skill from the `/` menu does nothing — use `$` instead

## Symptom

A skill is set up and works when invoked one way, but selecting the same skill from the `/` command menu in a chat inserts a mention that is silently ignored: the skill's instructions are never injected, the raw tag (e.g. `@es`) may remain visible in the sent message, and the model may respond as if it were asked to follow a "skill protocol" it invents on its own.

## Affects

Anyone selecting a skill from the `/` menu. Selecting the same skill from the `$` menu works correctly and is not affected.

## Cause

The `/` menu builds its mention differently from `$` and omits an attribute the backend needs to recognize which trigger character was used. The backend only recognizes skill mentions triggered by `$` (or `/` typed manually without using the menu); mentions built by the `/` menu are misidentified and dropped.

## Remedy

Use the `$` menu to select skills instead of the `/` menu until this is fixed upstream. Skills invoked this way inject correctly.

## Do not

- Don't assume the skill itself is broken or misconfigured — the same skill works fine via `$`.
- Don't tell the customer to recreate the skill — this is a selection-menu bug, not a skill-definition problem.

## Notes

As of this writing the issue is open and unfixed on upstream `main`; there is no version number to point to yet. If the customer needs to confirm they've hit this specifically (versus a broken skill), the message will show the wrong sigil (`@` instead of `$`) in front of the skill id after sending.
