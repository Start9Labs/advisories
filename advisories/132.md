# Fulcrum: Electrum (the desktop wallet) cannot connect to Fulcrum's SSL port on any address

## Symptom

Electrum (the official desktop/AppImage wallet) refuses to connect to Fulcrum's SSL address (`<host>:50002:s`, or whatever port Fulcrum's SSL interface actually shows) — LAN IP, `.local`, or a TLS'd onion all fail the same way. The GUI shows no error dialog; the log records:

```
interface.[<ip>:50002] | disconnecting due to: ErrorGettingSSLCertFromServer(
  ConnectError(SSLCertVerificationError(1, '[SSL: CERTIFICATE_VERIFY_FAILED]
  certificate verify failed: self signed certificate in certificate chain')))
```

Other wallets that prompt to accept/pin the certificate (e.g. Sparrow) connect fine — this only affects clients like Electrum that require either a publicly-trusted certificate or a bare self-signed one.

## Affects

Anyone connecting stock Electrum to Fulcrum's SSL (`:s`) address on any StartOS device. Installing the device's Root CA into the operating system's trust store does not help — Electrum ignores the system store and validates only against its own bundled CA list. Wallets that pin certificates on first connect (Sparrow, etc.) are not affected.

## Cause

StartOS serves a certificate chain (leaf ← Local Intermediate CA ← device Root CA) with the root sent in the handshake. Electrum's connection logic only accepts a publicly-trusted certificate or a bare self-signed leaf (OpenSSL verify code 18); StartOS's chain fails with verify code 19 (`self-signed certificate in certificate chain`), which Electrum treats as fatal rather than as a pinning opportunity.

## Remedy

Place the device's Root CA certificate (`/static/local-root-ca.crt`, the same file used for browser trust) into Electrum's certificate store for that host: `<datadir>/certs/<host>`, where `<host>` is exactly the address string typed into Electrum's server entry (server entry form `<host>:<port>:s`). `<datadir>` is `~/.electrum`, `~/Library/Application Support/Electrum`, or `%APPDATA%\Electrum` depending on platform. If a file already exists at that path, remove it first — a zero-byte or mismatched file silently blocks the connection with nothing logged. This has been confirmed on hardware against Electrum 4.6.2 for both LAN IP and `.local` addresses, and is durable: it pins the long-lived root rather than the leaf, so it survives normal certificate rotation.

## Do not

- Don't tell users to enable "SSL" in Electrum without the certificate step above — the connection will still be refused before that setting matters.
- Don't suggest running the plaintext (`:t`) port over the LAN as a fix — this sends every wallet query in the clear and is not something support should recommend.
- Don't suggest installing the device Root CA into the OS/browser trust store as a fix for Electrum — Electrum never consults it.

## Notes

- The identical issue and the identical fix apply to electrs — treat an electrs report of the same Electrum symptom as the same underlying situation.
- On a device migrated from StartOS 0.3.5.1 with electrs already installed, electrs may end up holding SSL on port 50001 instead of the usual 50002 (a port-reclaim artifact of the migration, not a fresh-install behavior) — always read the live port from the address shown rather than assuming a number.
- Untested / not to document yet: a Tor address added to Electrum's interface (`<onion>:50001:t`) is believed to work over the raw port by design, but has not been verified live.
- A separate, unrelated OS-side issue can cause repeated "certificate changed" warnings for pinning clients (Sparrow) on dual-stack networks — that is not this issue and is tracked separately upstream (start-technologies).
