# StartTunnel: inbound IPv6 connections to a delegated address hang until timeout — fix ships in StartTunnel 1.3.0

## Symptom

An inbound IPv6 connection to a server's tunnel-delegated global address (GUA) hangs and eventually times out, even though the equivalent IPv4 connection to the same server works fine. There is no error — the connection simply never completes. On the server, `conntrack` shows the inbound SYN was received but the entry stays `[UNREPLIED]`, e.g.:

```
tcp 6 104 SYN_SENT src=2001:470:... dst=...:f002 dport=443 [UNREPLIED] ... mark=1005
```

## Affects

Servers using StartTunnel with an IPv6 GUA delegated by the tunnel, receiving inbound connections over IPv6 to that address. IPv4 through the same tunnel is unaffected. Outbound IPv6 from a socket not bound to the tunnel address is unaffected by this fix and continues to be blocked by design.

## Cause

The SYN-ACK that opens the connection is routed by the kernel before StartOS's normal reply-routing hook runs, so it falls through to a catch-all route table and is dropped as a leak-guard blackhole instead of being sent back out the tunnel interface. IPv4 does not hit this because its catch-all table has a real default route.

## Remedy

This is fixed in StartTunnel 1.3.0. Update to that version; there is no workaround on earlier versions.

## Notes

Established connections and replies from sockets already bound to the tunnel address are not affected — only the initial SYN-ACK that opens a new inbound connection.
