# Service update fails with `rm ... No such file or directory` after a recent backup — stop the service first

## Symptom

Updating a service fails with an error like:

```
Updating Failed: Multiple Errors:
Filesystem I/O Error: rm /var/lib/lxc/<container>/rootfs/media/startos/volumes/main: No such file or directory (os error 2)
Filesystem I/O Error: rm /var/lib/lxc/<container>/rootfs/media/startos/assets: No such file or directory (os error 2)
Filesystem I/O Error: rm /var/lib/lxc/<container>/rootfs/usr/lib/startos/package: No such file or directory (os error 2)
```

The failing paths are always the service's complete set of volume/asset/package mountpoints. It happens on the first update attempt after the service was backed up and restarted, and only while the service is still running.

## Affects

Any service updated shortly after a backup run, while the service is running. Stopping the service first, then updating, succeeds. Not specific to one package — reported across multiple services (Vaultwarden, BTCPay Server, and others) on the same servers.

## Cause

Container teardown after a backup's stop/restart cycle leaves a duplicate teardown reference. When the update runs, two teardown tasks race to unmount and remove the same mountpoints; the losing task hits `ENOENT` on paths the winner already removed, and the update aborts even though teardown actually succeeded.

## Remedy

Known issue, under investigation. Until it's fixed: stop the service before updating it, especially if it was backed up recently. Updating a running service that was recently backed up is what triggers the race; updating a stopped service takes a single teardown path and succeeds.

## Do not

- Retry the update repeatedly without stopping the service first — the race reproduces the same way each time and the update will keep failing.

## Notes

- The underlying teardown data is intact — no data loss; this is an update-time failure, not a backup or restore problem.
- The same duplicated-teardown mechanism has also been observed causing a requested server restart to strand the box in diagnostic mode instead of rebooting (tracked as a related, separable fix), and a permanently wedged daemon runner requiring a manual Stop/Start. Those are more severe but rarer manifestations of the same root cause; this advisory covers the common update-failure case.
