# StartTunnel — devices get IPv6 addresses but have zero connectivity when the provider assigns the delegated block directly on the WAN interface

## Symptom

A tunneled device receives an IPv6 address but has no connectivity over it: the device can reach the server, but nothing ever comes back — no timeout message, just silence. On the server, `ip -6 route get <device-v6>` shows the route resolving to the WAN interface (e.g. `dev eth0`) instead of the WireGuard interface (`dev wg-start-tunnel`).

## Affects

Tunnel servers whose provider configures the delegated IPv6 block directly on the WAN interface at its exact size — DigitalOcean does this with a /124. Servers where the WAN address is configured at a different (larger) prefix than the delegated block are not affected.

## Cause

The WAN interface's on-link route and the WireGuard interface's Address-derived route end up with identical prefix length and metric, so the kernel's routing table resolves return traffic to the WAN interface instead of the tunnel. `wg-quick` does not install the per-peer /128 routes that would normally break this tie.

## Remedy

Update to StartTunnel 1.3.0, which installs an explicit /128 route over the WireGuard interface for every device address, resolving the tie in the tunnel's favor.
