# MLX backend uses excessive memory and causes heavy swapping during long agent conversations on Apple Silicon (ollama service)

## Symptom

Users running the `ollama` service with the MLX backend on Apple Silicon report the process's memory usage growing far beyond the model size during a single long-running conversation (e.g. an agent/coding-assistant session), leading to heavy macOS swap usage and memory pressure. Reported growth: an ~18 GB model climbing to 28-30+ GB resident, with 10+ GB of swap accumulating during a single ongoing conversation. Setting `LLAMA_ARG_CACHE_RAM=0` does not prevent it.

## Affects

- StartOS users running the `ollama` service on Apple Silicon hardware using the MLX backend, with a single long, active conversation/session (not switching between multiple threads).
- Most noticeable on memory-constrained systems (e.g. 32 GB unified memory) but the underlying unbounded growth affects any Apple Silicon host.
- Does not affect the GGUF/Metal (non-MLX) backend.

## Cause

The MLX prefix cache's memory budget was only enforced on inactive conversation paths (e.g. when an agent switches between multiple threads). A single active conversation was not subject to the same cap and could grow without bound, per a maintainer's confirmation.

## Remedy

Tell the customer:
- This is a confirmed bug in the MLX backend's prefix-cache memory accounting, acknowledged by an Ollama maintainer.
- A fix has been made so that both active and inactive conversation paths are now subject to the memory cap; it will ship in the next Ollama version. Update the `ollama` service once that version is available.
- In the meantime, if they hit heavy swapping during long MLX sessions, restarting the conversation/session (or restarting the service) will reclaim the memory.
- `LLAMA_ARG_CACHE_RAM=0` is not an effective workaround for this issue.

## Do not

- Do not suggest `LLAMA_ARG_CACHE_RAM=0` as a fix — it was tested and did not resolve the swap/memory growth.
- Do not tell users to disable the MLX backend permanently as the only option — the fix is landing upstream.

## Notes

- As of this writing the fix has been described by a maintainer as forthcoming ("will be available in the next version") but no specific version number was given; check current release notes before naming one.
- The 8 GiB figure discussed in the issue is an internal cache budget constant, not something users can currently tune via an environment variable.
