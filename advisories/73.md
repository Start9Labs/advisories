# SimpleX Server: published SMP/XFTP address shows `undefined` and can't be authenticated after install or reinstall — update to 7.0.1:1

## Symptom

Right after installing SimpleX Server, or after reinstalling it, the SMP or XFTP address shown for the service looks malformed, containing `undefined` where the fingerprint should be — for example `smp://undefined:[redacted]@relay.example:5223`. The address is well-formed enough for a client to accept and store, but it cannot be authenticated against, so clients relying on it (including relays that resolve this server as a Local relay) fail silently or connect to the wrong identity.

## Affects

Fresh installs and reinstalls of SimpleX Server prior to version 7.0.1:1. Every fresh install and reinstall hits the underlying init-order bug (it recurs with a fresh CA each time), though the bad address is sometimes self-corrected by a later retry pass before anyone notices. Updates that are not reinstalls are not affected.

## Cause

An init step (`setInterfaces`) that publishes the server's addresses ran before the step that generates the server's fingerprint and password (`initServers`, which runs `smp-server init`). On a fresh install, `setInterfaces` read an empty fingerprint file and empty password, producing the `undefined` address. The steps have been reordered so the fingerprint and password are always generated first.

## Remedy

Update to SimpleX Server 7.0.1:1. If the service was installed or reinstalled on an older version, re-fetch the SMP/XFTP address after updating and re-share it with anyone or anything (including dependent relays) that had picked up the malformed `undefined` address — the old value will not fix itself.

## Notes

Surfaced via the SimpleX WebSocket Bridge, which resolves this interface as its Local relay and picked up the malformed address while following a reinstalled server; that package separately added a defensive shape guard, but the fix for the bad address belongs here.
