# SearXNG: search results are slower than they should be because the cache is silently unused — fixed in 2026.8.29:1

## Symptom

Nothing overt fails: searches still return results, and the web interface works normally. But the SearXNG cache was never actually reachable — `valkeydb.initialize()` always returned `False` — so every search runs uncached. There is no error visible in the UI; it can only be seen in the SearXNG log as a Valkey connection failure at startup, or by checking that results feel slower than expected on repeat queries.

## Affects

Everyone running SearXNG `2026.8.29:0` (and every earlier version, back to commit `57be8b8`, which introduced the unix-socket cache URL). Both fresh installs and existing installs updated from an earlier version are affected equally, since the cache has never worked since it switched to a socket URL.

## Cause

Valkey listened on a unix socket (`/var/run/valkey.sock`) inside its own subcontainer, while SearXNG ran in a different subcontainer that does not share `/run` with it, so the socket path SearXNG was configured to use never existed from its side. The connection silently failed every time.

## Remedy

Update to SearXNG `2026.8.29:1`. Valkey now binds to `127.0.0.1:6379` instead of a unix socket, since subcontainers share the container's network namespace, and `settings.yml`'s `valkey.url` is rewritten automatically on update from the stale socket URL to `valkey://127.0.0.1:6379/0`. No further action is needed after updating.

## Notes

This version also bumps the bundled Valkey image from 8-alpine to 9-alpine; no data migration applies since Valkey runs with `--save '' --appendonly no` and no volume mounted, so there was never anything on disk to migrate.
