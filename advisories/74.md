# Gitea Runner shows healthy while crash-looping and processing no jobs — fixed in 3.3.0:1

## Symptom

The service's health check reports `success | Runner is running` even though the runner is stuck in a crash loop, restarting roughly every 2 minutes and picking up no jobs. Nothing in the StartOS UI indicates a problem — the status stays green through the outage. If the daemon dies (for example the registration token is invalidated), the crash message `primary daemon crashed` can briefly show but is then overwritten back to a green `success` on the next 30-second poll.

## Affects

Anyone running Gitea Runner before version 3.3.0:1. Caused by the health check testing only for the presence of the `runner/.runner` registration file, which persists across crashes and says nothing about whether the runner process or its connection to the container engine is actually working.

## Cause

`ready.fn` judged health on whether registration had ever completed, not on whether the daemon was currently running. A completed registration file remains on disk through a crash loop, and the periodic health poll overwrote the SDK's own crash status with a stale green result almost every time it ran.

## Remedy

Update to Gitea Runner 3.3.0:1 (or newer). The health check now requires both a live `gitea-runner` process and a working connection to the container engine's API socket before reporting success, so a crash loop or lost engine connection now shows as failing health instead of green.

## Notes

If jobs stop being picked up despite a green status, that mismatch is exactly what this fix addresses — updating resolves it without any other action needed.
