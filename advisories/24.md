# Jellyfin 12.0 crashes seconds after login when the library has a large playlist

## Symptom

After updating to Jellyfin 12.0, the server runs normally until someone logs in. Loading the home screen sends its memory from a few hundred MB to several GB within seconds and the process is killed: the home screen stays blank or spinning, every client drops, and it happens again on the next login. The log shows no error at the moment it dies — the last line is ordinary and the next is a fresh startup banner. It can also die with nobody using it, more slowly.

## Affects

Jellyfin 12.0 with at least one large playlist — thousands of items. One such playlist is enough whatever the size of the rest of the library. Servers with no playlists, or only small ones, are not affected.

## Cause

The query that builds the home screen joins each playlist against its items. A playlist's row in `BaseItems` also embeds its whole item list, with full paths, in its `Data` JSON, so the join repeats that already-large row once per item and sorts the result. Memory grows with the square of the playlist's size, and one large playlist produces tens of GB of temporary sort data. Upstream Jellyfin behaviour, nothing StartOS-specific.

## Remedy

- A known Jellyfin 12.0 bug. No Jellyfin release fixes it yet.
- The workaround is a one-time repair of Jellyfin's database, `jellyfin.db`, made with Jellyfin stopped and the database backed up first:
  ```sql
  UPDATE BaseItems SET Data = json_remove(Data, '$.LinkedChildren')
    WHERE Data LIKE '%"LinkedChildren"%';
  ```
  It removes the embedded copy of each playlist's item list; the list itself lives in the `LinkedChildren` table and is untouched, so playlists keep working. Several reporters confirm the crash stops, memory returns to normal and the home screen loads.
- Until the repair is made, every login that loads the home screen brings Jellyfin down again.

## Do not

- Do not suggest more memory. Growth is quadratic in playlist size and reaches tens of GB, so no limit is a fix.
- Do not treat it as a StartOS packaging problem — it reproduces on the official Jellyfin image everywhere.

## Notes

- The `jellyfin/jellyfin` 12.0 image ships no `sqlite3` command, so the repair cannot be run from inside the service's container; it needs `sqlite3` wherever the database file can be reached.
- On StartOS the database is in the package's `config` volume, at `data/jellyfin.db`.
- Deleting the large playlist should avoid it too, going by the cause, but nobody has confirmed that — unconfirmed; do not offer it as the fix.
- jellyfin/jellyfin#17881 is merged for 12.1 and fixes #17871, a box-set case on the same home-screen query. Whether it covers playlists is not confirmed, so there is no version to name.
- jellyfin/jellyfin#17884, also merged for 12.1, addresses a separate memory issue: folders retaining their scanned children during a library scan (fixes #17860). It targets the scan/validate phase, not the home-screen playlist join this advisory covers, and a benchmark in the discussion found no measurable memory gain from it at library sizes without the retention problem dominating. Not a fix for this issue.
