# Jellyfin 12.0 memory spikes to multiple GB and gets OOM-killed after login

## Symptom

After upgrading to Jellyfin 12.0, the server sits at a normal idle memory level, but shortly after a user logs in (loading the home screen), memory use spikes from a few hundred MB to several GB within seconds, and the process is killed. The server log shows nothing at the moment of death — no exception, no stack trace — it just stops and the next log line is a fresh startup banner.

## Affects

Users running Jellyfin 12.0 who have at least one large playlist (many items) in their library. The bug is triggered by loading the home screen / user views after login, not by any particular library size otherwise — a single large playlist is enough regardless of how many other items exist. Servers with no playlists, or only small playlists, are not affected.

## Cause

A database query used to build the home screen joins `BaseItems` against `LinkedChildren`. Each playlist's `BaseItems.Data` JSON column separately embeds its own full `LinkedChildren` list (with full paths), so that already-large row gets repeated once per joined child row in the query. Memory use grows quadratically with playlist size, so one large playlist can multiply into tens of GB of temporary sort data and exhaust memory. This is upstream Jellyfin behavior, not anything StartOS-specific.

## Remedy

Tell the customer:
- This is a known upstream Jellyfin 12.0 bug affecting servers with large playlists, still open and not yet fixed in a release as of this writing.
- Back up the Jellyfin database first.
- As a workaround, run the following SQL against the Jellyfin database to strip the redundant embedded data (this does not affect the separate LinkedChildren table or playlist functionality):
  ```sql
  UPDATE BaseItems SET Data = json_remove(Data, '$.LinkedChildren')
    WHERE Data LIKE '%"LinkedChildren"%';
  ```
- Multiple reporters confirm this resolves the crash and restores normal memory use and home screen loading, with playlists still working afterward.
- Watch for a future Jellyfin release that fixes this properly; check back before applying further workarounds.

## Do not

- Do not suggest simply raising the memory limit or container `mem_limit` — the growth is quadratic in playlist size and can reach tens of GB, so this is not a reliable fix.
- Do not assume this is a StartOS packaging issue — it reproduces on official Jellyfin Docker images outside StartOS as well.

## Notes

- Reported independently by several users on different platforms (Synology Docker, plain Docker) with consistent measurements, and the workaround has been confirmed by at least three separate reporters.
- A related upstream issue/PR (#17871, #17881) may address the same code path with a proper fix; there is no confirmed release version yet, so do not name one.
