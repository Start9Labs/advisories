# Uptime Kuma: memory grows continuously with TCP monitors that use TLS/StartTLS cert checks — fixed in 2.5.5

## Symptom

Uptime Kuma's memory usage climbs steadily over hours to days — reports range from several hundred MB to multiple GB — and only drops back to normal after restarting the container. `lsof` or `ss -s` on the container shows a large and growing number of closed-but-still-referenced TCP sockets. The problem occurs with both the slim (MariaDB/external DB) and regular (SQLite) images.

## Affects

Uptime Kuma 2.5.4 and earlier, on any install with one or more TCP monitors that have the TLS certificate check enabled (including STARTTLS-style checks on protocols like SMTP, IMAP, POP, MQTT). HTTPS monitors with cert checks and plain TCP monitors without a cert check are not affected. Lower monitor check intervals make the leak worse and faster to notice.

## Cause

A regression from the TCP monitor rewrite in upstream PR #6401: sockets opened for the TLS/STARTTLS certificate check were not being closed correctly in some cases, leaving them referenced and their memory unreclaimed.

## Remedy

Update to Uptime Kuma 2.5.5 or newer once it is available in the Start9 registries; the maintainer has confirmed the fix resolves the leak. Until then, if memory growth is causing problems, increasing the check interval on affected TCP/TLS monitors slows the leak, and restarting the service reclaims the memory.

## Notes

StartOS currently ships up to 2.5.4:0 in all three registries; 2.5.5 had not yet appeared in any Start9 registry as of this writing.
