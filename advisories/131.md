# Datum Gateway stratum port unreachable from a separate VLAN or routed subnet — fixed in StartOS 0.4.0.2

## Symptom

A device on a different subnet than the StartOS host's own LAN (for example a separate VLAN routed to the host, with routing and ACLs confirmed to allow the traffic — `ping` succeeds) cannot reach Datum Gateway's stratum port. `nc -zv <host-ip> 23334` fails, and Datum Gateway logs nothing at all about the attempt.

## Affects

StartOS 0.4.0.1 and earlier, for anyone reaching a service's plain (non-SSL) port — most often Datum Gateway's stratum port, since Bitaxe miners tend to sit on a separate IoT or guest network — from a private subnet other than the StartOS host's own on-link LAN subnet. Devices on the same subnet as the StartOS host are not affected. The StartOS admin UI and service web interfaces are not affected: they already accept any private-range source.

## Cause

StartOS source-filters a service's plain LAN port to the host's own on-link subnet and the container bridge, so a connection from a separate routed subnet is dropped before it reaches Datum Gateway. Web interfaces take a different path that accepts any private-range source, which is why only plain ports are affected. This is StartOS behavior, not a Datum Gateway bug.

## Remedy

Fixed in StartOS 0.4.0.2, the next release: a service's plain port then accepts connections from any private (RFC 1918) IPv4 network routed to the server. Datum Gateway itself needs no update. Until 0.4.0.2 is out, a hand-added `nft` rule for the other subnet (mirroring the existing per-subnet DNAT rule) restores connectivity, but it is lost on reboot or whenever StartOS regenerates the service's networking.

## Do not

- Do not treat this as a Datum Gateway misconfiguration or routing problem — routing, ACLs and masquerade all work; only the source-subnet filter on the plain port blocks it.
- Do not expect the manual `nft` rule to survive a reboot or a service config change.
