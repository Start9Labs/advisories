# Database-backed services (btcpayserver, ghost, immich, mattermost, nextcloud, synapse, and others) — a failed backup can silently destroy the last good one, but the UI still shows it as valid

## Symptom

A backup for a database-backed service fails partway through, but the dashboard continues to list a previous backup as present and valid — same timestamp, version and title as before. Nothing indicates that backup is now broken. The problem only surfaces when a restore is attempted from that target: the database restore fails or restores a truncated/incomplete dump, because the file the metadata pointed to was overwritten mid-copy by the failed run and never completed.

## Affects

Anyone backing up a package that uses the SDK's `withPgDump` or `withMysqlDump` helper — in the official registry this includes btcpayserver, cal-diy, ghost, immich, mattermost, nextcloud, spliit and synapse — to a target that has exactly one backup slot per package (the normal case; there is no snapshotting). It is triggered by anything that interrupts the database-dump copy step: a backup that times out or is killed partway (see advisory 4), a full target, an unplugged or disconnected drive, or a target-side I/O error. Volume/file data is not affected — only the database dump copy is at risk. Services that don't use these dump helpers are not affected.

## Cause

The dump is copied straight over the final path on the backup target (`cp` with truncate-and-stream), with no staging file and rename, so an interruption leaves a truncated file exactly where the last good dump was. Separately, when a backup fails, StartOS skips recording the new (failed) backup but also does not clear or invalidate the existing metadata entry, so the dashboard keeps advertising the old backup as good even though its underlying file has already been overwritten.

## Remedy

There is no fix yet; this is confirmed and tracked upstream. Until it ships:

- Treat a failed backup as reason to distrust the *existing* backup for that package on that target, not just the attempted one — the previous good dump may already be gone.
- After any failed backup of one of the affected services, do not rely on that target's existing backup; take a fresh backup once the underlying cause (target full, drive unplugged, timeout, etc.) is resolved, and confirm it succeeds.
- Periodically test-restore backups of these services rather than trusting that a listed backup is restorable.

## Do not

- Assume a backup shown in the UI is good just because a later backup attempt failed — the failed attempt itself may have already destroyed it.
- Wait for a restore to find out — by then the previous dump may be unrecoverable.

## Notes

- This is a separate defect from advisory 4 (the 30-second `cp` timeout causing `SIGKILL`); that timeout is one trigger among several (full disk, unplugged drive, power loss, I/O error) that can hit this data-loss path, and fixing the timeout alone does not fix this.
- The restore side has a related but lower-risk issue: a truncated staged dump is copied to `/tmp` inside the subcontainer before being handed to the database restore tool, so a failure there doesn't touch data on the backup target but can still cause a restore to fail or silently use an incomplete dump.
