# Immich, Ghost, Mattermost, Discourse, Cal.com, Firefly III: "Set Primary URL" task returns each morning and the service is stopped — the LAN link dropped overnight; re-select the same URL and start it

## Symptom

A critical "Set Primary URL" task appears on the service, with the reason "Primary URL removed. Select a new primary URL." (Discourse: "Discourse cannot start without a primary URL"), and the service is stopped. Opening the action shows the address the user already chose, usually the `.local` one, still listed and still selectable. Re-selecting it clears the task, and it is back the next morning, "every day". Nothing about the server's name, Tor, domains or gateways changed, and the server itself did not restart.

## Affects

Services whose primary URL is the server's `.local` address or a LAN IP, on StartOS 0.4.0 and 0.4.0.1. The trigger is the server losing its LAN link while running: a router or switch that restarts on a nightly schedule is the confirmed case, and a pulled cable or a Wi-Fi drop does the same. A server that starts before its network is up, because it boots alongside its router or on Wi-Fi, hits the same path; an ordinary restart with the network already up does not. Immich, Ghost, Mattermost, Discourse, Cal.com and Firefly III raise the task as critical, which stops the service; bolt12-pay and Miniflux from the community registry do the same. Linkwarden, Memos and Multi-Scrobbler raise it at a lower severity, so the task appears but the service keeps running. A service whose primary URL is a Tor address or a domain is not affected, and neither is a service with no primary-URL setting.

## Cause

Each of these packages checks its stored primary URL against the addresses the service can be reached at, re-runs that check whenever the address list changes, and raises the task when the URL is missing. When the LAN link drops, the LAN IP leaves the list and, since SDK 2.0 (July 2026), the `.local` address counts as missing while no LAN IP is up on its interface, so the check fires the moment the link goes. The task is never withdrawn once the address is back, and a critical task stops the service.

## Remedy

Run "Set Primary URL", select the same address that was selected before, then start the service. The choice is stored and intact; nothing else needs changing. The task will return after the next link drop until the fix ships.

If the service has a Tor address or a domain and links generated on that address suit the user, selecting it as the primary URL stops the recurrence, because those entries do not depend on the LAN link. If the router's nightly restart is a schedule the user set, turning it off stops the recurrence too.

Fixes are in review on the StartOS side, for 0.4.0.2, and on the SDK side, for the packages' next rebuild on SDK 3.0; neither has shipped.

## Do not

- Don't chase a change to the server name, Tor, DNS or a domain: the address never went away for good, the check ran while the link was down.
- Don't suggest a reinstall, a restore, or disabling and re-enabling the `.local` address: none of them touch the cause, and the stored URL is already correct.
- Don't suggest a LAN IP as a sturdier primary: it leaves the list in the same moment as `.local`.
- Don't tell the user a reboot causes it: a server restarted with its network up does not see this.

## Notes

A task raised because the user genuinely removed the address (deleted the domain, uninstalled Tor, renamed the server) is correct and is not this; there, the previously chosen address is gone from the action's list. In this situation it is still listed. The reporting user's router restarts every night, confirmed 2026-09-21. As of that date the StartOS fix (#4031) and the SDK helper the packages will adopt (#4030) are open pull requests; update this advisory when 0.4.0.2 ships and again as each package's SDK 3.0 rebuild reaches the registry, since the rebuild is what stops the task for that service.
