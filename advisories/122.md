# Immich, Ghost, Mattermost, Discourse, Cal.com, Firefly III: "Set Primary URL" task comes back after a reboot and the service stops — re-select the same URL and start it

## Symptom

A critical "Set Primary URL" task appears on the service, with the reason "Primary URL removed. Select a new primary URL." (Discourse: "Discourse cannot start without a primary URL"), and the service is stopped. Opening the action shows the address the user already chose, usually the `.local` one, still listed and still selectable. Re-selecting it clears the task, and it returns the next time the server restarts, often "every day" or "every morning" on a server that is shut down or loses its network overnight. Nothing about the server's name, Tor, domains or gateways changed.

## Affects

Services whose primary URL is the server's `.local` address or a LAN IP, on StartOS 0.4.0 and 0.4.0.1. The trigger is a server restart, or the server losing its LAN link for a moment: a router reboot, a pulled cable, a Wi-Fi drop. Immich, Ghost, Mattermost, Discourse, Cal.com and Firefly III raise the task as critical, which stops the service; bolt12-pay and Miniflux from the community registry do the same. Linkwarden, Memos and Multi-Scrobbler raise it at a lower severity, so the task appears but the service keeps running. A service whose primary URL is a Tor address or a domain is not affected, and neither is a service with no primary-URL setting.

## Cause

At boot StartOS rebuilds every service's address list before NetworkManager has reported the interfaces, so for a moment the list holds no `.local` or LAN IP entries; the same rebuild happens whenever an interface changes. Each of these packages checks its stored primary URL against that list from its init hook, re-runs the check on every change, and raises the task when the URL is missing. It never withdraws the task once the address is back, and a critical task stops the service. Since SDK 2.0 (July 2026) a `.local` address also counts as missing while no LAN IP is up on its interface, so a link that is down for a second is enough.

## Remedy

Run "Set Primary URL", select the same address that was selected before, then start the service. The choice is stored and intact; nothing else needs changing. The task will return on the next restart or link drop until the fix ships.

If the service has a Tor address or a domain and links generated on that address suit the user, selecting it as the primary URL stops the recurrence, because those entries survive the rebuild.

Fixes are in review on the StartOS side, for 0.4.0.2, and on the SDK side, for the packages' next rebuild on SDK 3.0; neither has shipped.

## Do not

- Don't chase a change to the server name, Tor, DNS or a domain: the address never went away, the check ran while the list was being rebuilt.
- Don't suggest a reinstall, a restore, or disabling and re-enabling the `.local` address: none of them touch the cause, and the stored URL is already correct.
- Don't suggest a LAN IP as a sturdier primary: it is rebuilt in the same pass as `.local` and has the same exposure.

## Notes

A task raised because the user genuinely removed the address (deleted the domain, uninstalled Tor, renamed the server) is correct and is not this; there, the previously chosen address is gone from the action's list. In this situation it is still listed. As of 2026-09-20 the StartOS fix (#4031) and the SDK helper the packages will adopt (#4030) are open pull requests; update this advisory when 0.4.0.2 ships and again as each package's SDK 3.0 rebuild reaches the registry, since the rebuild is what stops the task for that service.
