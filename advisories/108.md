# StartOS gets stuck on the diagnostic screen after a Restart or Shutdown instead of powering off

## Symptom

After choosing Restart or Shutdown, all services stop normally in the logs, but the server never finishes shutting down — it sits on the diagnostic UI screen instead. This can persist for a long time (seen for 33 minutes) until `startd` is stopped by hand. The OS log around the time of the stall shows errors like:

```
rm <container>/rootfs/media/startos/volumes/main: No such file or directory (os error 2)
rm <container>/rootfs/media/startos/assets:       No such file or directory (os error 2)
rm <container>/rootfs/usr/lib/startos/package:    No such file or directory (os error 2)
```

followed by a `Multiple Errors` message from `start_core::bins::startd`.

## Affects

Anyone doing a Restart or Shutdown on 0.4.0, 0.4.0.1, or (currently) master/0.4.0.2 — it is a timing race during service teardown, not tied to a particular service, config, or number of packages. It fires intermittently (observed once in about 11 weeks of normal shutdowns on one box) rather than every time.

## Cause

During shutdown, each service's mountpoints can be unmounted twice — once from the shutdown path, once from a detached cleanup task — within milliseconds of each other. The second attempt finds the mountpoint already removed and gets `ENOENT`, which the shutdown code treats as a hard error instead of the successful outcome it actually is. That error propagates out of `inner_main`, and StartOS treats any error there as a startup failure, so it serves the diagnostic UI rather than completing the shutdown.

## Remedy

If a Restart or Shutdown appears to hang on the diagnostic screen, the shutdown has actually completed on the service side already — stopping/restarting `startd` finishes powering off or rebooting. This is known and fixed; the fix (tolerating `ENOENT` as success during mountpoint teardown) is merged and ships in 0.4.0.2.

## Do not

- Do not treat this as a hardware or service-specific problem — the affected services log a normal shutdown, and the hang is in the teardown/diagnostic-mode logic, not in the containers.

## Notes

A maintainer confirmed the direction on 2026-09-18: teardown should be idempotent, tolerating `ENOENT` from `remove_dir` in `unmount_slot`, and likewise for `unmount` on an already-gone path. The double-unmount race itself (a detached `MountGuard::drop` task racing the shutdown path's own unmount) is flagged by the reporter as worth a separate look, but is not required for this fix.
