# StartWRT — publishing a port to a device with no hostname can take down DHCP/DNS — fix ships in 1.2.0

## Symptom

After publishing a port to a device on the LAN, DHCP and DNS stop working for the whole network. The router's log shows:

```
daemon.crit dnsmasq[1]: bad DHCP host name at line 29 of /var/etc/dnsmasq.conf.cfg01411c
daemon.crit dnsmasq[1]: FAILED to start up
```

This happens for a device that never advertised a hostname of its own — the reservation gets written with a generated display label like `Android device (4c8f63)`, which dnsmasq refuses, and it takes DHCP down with it.

## Affects

Anyone publishing a port to a device with no reserved address yet, where that device has not advertised its own hostname (so StartWRT shows it under a generated label). Devices that already advertise a hostname are not affected.

## Cause

The reserve path sent the device's resolved display name — a learned hostname or a generated label — into the DHCP reservation's name field. dnsmasq will not start with a generated label in that field, and a single bad reservation stops the whole DHCP/DNS service.

## Remedy

Update to StartWRT 1.2.0, which stops sending the generated label into the reservation, validates the name/mac/ipv4 fields before writing them, and heals any existing bad name automatically at boot.

For a router already stuck with DHCP/DNS down: an update cannot be started from a router in that state. Reflash from microSD with the "Keep settings" option — this restores the existing configuration, including the bad name, onto firmware whose first boot repairs it automatically.

## Notes

Once healed, the UI may keep showing the old (cleared) name until the device's next DHCP lease renewal — that is a separate, pre-existing display quirk, not a sign the repair failed.
