# StartOS server becomes completely unresponsive under memory pressure (no journal entries) — fix ships in 0.4.0.2

## Symptom

Under memory pressure, the server becomes unreachable at every level — no SSH, no HTTPS, not even ARP — as if it were powered off. A forced power cycle is needed to bring it back. The journal shows nothing: no error, no warning, just a gap where logging stops. Any service that was mid-write (for example, mid-install or mid-backup) can lose data. `oomctl` may show `Swap Usage: 0B` for `/services.slice` even while the kernel accounts several GiB of swap use in that same cgroup — this reading is a stale cache and not evidence the safeguard is broken by itself.

## Affects

Any StartOS server running with zram swap enabled (the default) that comes under sustained memory pressure — for example many packages installed, or a heavy install/backup running concurrently with normal service load. Not limited to any particular package count, but more packages installed increases the chance any one workload tips the box into this state.

## Cause

StartOS's container-memory protection relies on `systemd-oomd` to kill a runaway service before the whole host runs out of memory. On a zram-swap system, zram's compressed pages are not charged to the `services.slice` cgroup, so services plus their compressed swap footprint can exceed the memory reserved for the host, and `systemd-oomd`'s swap- and pressure-based triggers can both fail to select a victim in time (fragmented swap usage across many small cgroups, or pressure that never crosses the kill threshold before the host itself is starved). The result is a global out-of-memory condition that can wedge the host before the kernel's own last-resort OOM killer acts, and that killer can end up targeting the wrong process.

## Remedy

This is fixed in StartOS 0.4.0.2: zram swap is now off by default on fresh installs, and the update to 0.4.0.2 disables it on existing servers automatically as part of the migration. Customers who update to 0.4.0.2 do not need to do anything further. An experimental CLI control remains for anyone who wants to re-enable zram explicitly, but doing so restores the risk of this wedge.

## Notes

The `oomctl ... Swap Usage: 0B` line is a display artifact of a stale cache and does not by itself mean the safeguard is inactive — it can appear on entirely healthy systems too. The distinguishing symptom is the full host wedge (no journal entries, no network response of any kind, requires a power cycle), not the 0B reading alone.
