# Immich: closing the mobile app can crash the server and restart the container

## Symptom

The Immich server container restarts unexpectedly, often shortly after the mobile app is closed or finishes a background sync. Server logs show an unhandled socket error immediately before the restart:

```
node:events:486
      throw er; // Unhandled 'error' event
Error: read ECONNRESET
    at TCP.onStreamRead (node:internal/stream_base_commons:216:20)
Emitted 'error' event on Socket instance at:
    at emitErrorNT (node:internal/streams/destroy:170:8)
    at emitErrorCloseNT (node:internal/streams/destroy:129:3)
api worker exited with code 1
```

Every request beforehand succeeded — there is no error tied to any particular upload or route. With the app in the foreground the crash follows a `Websocket Disconnect` line by roughly 300–400ms; with the app backgrounded (sync only, no uploads) it follows the last `POST /api/sync/ack 204` by about a second.

## Affects

Anyone running the Immich mobile app against their server — this happens on ordinary use (closing the app, or its periodic background sync), not any particular feature or configuration. It reproduces intermittently, roughly one in three app-close cycles in the reported case.

## Cause

Immich's HTTP server never attached an `'error'` listener to sockets it accepts. When a client (e.g. the mobile app) resets the connection after its requests have already completed — such as when the app is closed — Node's default behavior for an unhandled `'error'` event on that socket is to throw, crashing the whole process and restarting the container.

## Remedy

This is fixed upstream: the server now attaches an error handler to every accepted socket for its lifetime, so a connection reset from a closing client is logged and discarded instead of crashing the process. The fix has merged but is not yet in an Immich release available on StartOS; it will reach StartOS once a release containing it is published. No action prevents this in the meantime beyond expecting occasional container restarts tied to closing the app.

## Notes

No data loss occurs — every prior request already completed successfully before the crash, and the container restart is the only visible effect.
