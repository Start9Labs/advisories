# CryptPad — Launch button opens the wrong address and login appears to fail with correct credentials

## Symptom

Clicking **Open UI** / **Launch** for CryptPad loads the app on an address different from the one CryptPad was configured with (its Main URL). On that mismatched origin, a correct username and password appear to be rejected as invalid — CryptPad derives account/key material from the origin, so logging in from the "wrong" address does not work even though the credentials are right.

## Affects

CryptPad installs with more than one enabled address on the Main interface (for example, both a LAN/mDNS address and a Tor or clearnet domain), where the administrator has set a specific one as the Main URL. Opening StartOS, and clicking Launch, from a different access route than the one used to set the Main URL is what triggers it. Not affected: installs with only one address enabled on the Main interface.

## Cause

StartOS's Launch button opens the best address for however you are currently connected to StartOS (LAN, mDNS, Tor, domain, etc.), not the address the package was configured with. CryptPad has no way to tell the launcher which address is its configured primary origin, so the two can disagree.

## Remedy

Disable every address on CryptPad's Main interface except the one set as its Main URL (and likewise for the Sandbox interface, if used). With only one enabled address, Launch always opens that address regardless of access route. This is a StartOS/CryptPad interaction that no CryptPad or StartOS version currently resolves; a fix is tracked separately as a feature request (start-technologies#3715).

## Do not

- Do not treat this as a CryptPad login bug or account-recovery case — the credentials are correct; the origin is wrong.
- Do not tell them to just update StartOS or CryptPad — no shipped version fixes this.

## Notes

The same mismatch can in principle affect other packages with a package-configured canonical URL (Ghost, Gitea, Vaultwarden, Synapse, DocuSeal), but CryptPad is the only confirmed case where it produces a visible failure, because CryptPad's origin feeds into client-side key derivation.
