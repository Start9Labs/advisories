# StartOS shows a duplicate "Web UI" (or other interface) entry after a service update moves its internal port

## Symptom

After updating a service whose internal port for an interface changes (for example Web UI moving from port 80 to 8000), the Interfaces page shows two entries for the same interface — one stale, one live. The Launch button, port-forward labels, or the interface callback can resolve to the wrong (stale, dormant) entry instead of the current one, since StartOS picks whichever binding has the lower port number.

## Affects

Any StartOS user who updates a package that changes the internal port of one of its exported interfaces. Not specific to any one service — Jitsi is the example that surfaced it, but the defect is in StartOS's interface-export logic, not in the package.

## Cause

`clear_service_interfaces` retained old interface records by id alone, so when a package update rebinds an interface to a new internal port, the old binding's exported record was never removed. `find_service_interface` then scanned bindings in port order and could return the stale record instead of the current one.

## Remedy

Fixed in start-technologies PR #3639 (merged 2026-08-10): interface records are now removed from every prior binding before being re-inserted at the current one, so an interface id lives in exactly one place. Existing stale duplicate records self-heal automatically the next time the affected service is initialized — this happens on install, update, restore, rebuild, or server boot (a StartOS update's reboot re-inits every installed service), so no separate repair step is needed once the fix has shipped.

## Notes

No frontend change was needed — the UI was correctly rendering whatever the database contained; the bug was in the backend record-keeping.
