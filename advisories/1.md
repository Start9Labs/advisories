# Bitcoin Knots from the third-party registry start9.mempool.guide follows a different blockchain — there is no migration back to Bitcoin Core

## Symptom

A user has installed, or is asking about, a service called **Bitcoin Knots** obtained from a registry that is not the Start9 Registry or the Community Registry — the one at `start9.mempool.guide`. Its version is 29.4.1 (`#knots:29.4.1:5`, `:6` or `:7`), and it installs only on StartOS 0.4. StartOS raised no objection when they installed services against it, but its block height does not match Bitcoin's, expected transactions never appear, and no option is offered to switch it to Bitcoin Core. Those dependent services may separately show Bitcoin as an unsatisfied dependency, which is confusing on top of everything else. Just as often they simply ask whether it is safe to install.

## Affects

Anyone who installed Bitcoin Knots from a registry other than the Start9 Registry or the Community Registry, and every service on that server that depends on Bitcoin. Not anyone running the Community Registry's Bitcoin Knots, on any StartOS version — that one is Bitcoin.

## Cause

That package uses the `bitcoind` package ID and the `knots` flavor, so StartOS takes it for a flavor of Bitcoin. Its own version satisfies no ordinary Bitcoin version range. Versions `29.4.1:5` and `29.4.1:6` declared that they satisfy Bitcoin Core revisions `28.4:23` and `29.4:10`, and those two declarations were the entire reason anything accepted them: the Marketplace honours them, so it offered the install and warned nobody, while a service's own dependency check does not read them and can report Bitcoin as unsatisfied once installed. The two layers disagree, which is why the situation looks inconsistent rather than simply broken. The current `29.4.1:7` declares nothing, so nothing accepts a fresh install of it as Bitcoin — dependents show Bitcoin as unsatisfied from the start. It is not Bitcoin: it follows the chain that split from Bitcoin at BIP-110 (RDTS) and then hard-forked to a different proof-of-work algorithm.

## Remedy

- **Not yet installed** — do not install it unless they specifically intend to run that chain and understand that nothing else on their server should be pointed at it.
- **Already installed** — StartOS will not migrate it back. Bitcoin Core and Bitcoin Knots (pre-RDTS) both refuse a migration from it, so no flavor switch is offered and none can be made to appear. Returning to Bitcoin means uninstalling it and installing Bitcoin Core (Start9 Registry) or Bitcoin Knots (pre-RDTS) (Community Registry) fresh, and that is a full re-sync — the data directory holds the other chain's blocks and cannot be reused.
- **A Lightning node or wallet has been running against it** — escalate to a human. Its channel and wallet state was built against a different chain, and what can be recovered is not a question to answer from this entry.

## Do not

- **Do not describe that chain as broken, stalled, or failing to produce blocks.** It produces blocks normally. It is a different network, not a malfunctioning one — saying otherwise is wrong and the user can immediately see that it is wrong.
- **Do not suggest switching flavors as the fix.** StartOS offers no such switch here. Telling someone to look for one wastes their time and costs you the rest of the answer.
- **Do not confuse it with the Community Registry's Bitcoin Knots.** **Bitcoin Knots (pre-RDTS)** — package id `bitcoind`, flavor `knotsprerdts`, pinned at Knots 29.3, the last release before RDTS; a 0.3.5.1 server sees it as **Bitcoin Knots 29.3.0** — follows the same chain as Bitcoin Core, and switching between it and Core is supported and safe. It is a community package (`Start9-Community/bitcoin-knots-prerdts-startos`), not maintained or supported by Start9, but it is Bitcoin. Establish which registry a user's Knots came from before saying anything else about it: a Knots at 29.3 is the Community Registry's, a Knots at 29.4.1 is this one, and a user who names neither a registry nor a version gets that question before any of the above.
- **Do not tell a 0.3.5.1 user that Knots needs StartOS 0.4.** The Community Registry publishes Bitcoin Knots 29.3.0 for 0.3.5.1; only the 0.4 build carries the "(pre-RDTS)" suffix.
- **Do not present it as vetted or supported.** Start9 does not vet, endorse, or support services from registries other than the two that ship with StartOS.

## Notes

- With `29.4.1:5` or `:6` installed, the services that accepted it as Bitcoin include LND, Core Lightning, BTCPay Server, Fulcrum, electrs, Mempool, Specter, Bisq, Jam, Bitcoin Explorer, Fedimint, Public Pool, UTXOracle and Wasabi — the great majority of anything that depends on Bitcoin. Dojo, Eclair and Stratum V2 happen to require Bitcoin Core 31.x and therefore rejected it. Both Electrum servers accepted it, which matters because that is the path most wallets use to reach a node.
- Updating an installed `:5` or `:6` to `:7` should leave every dependent's Bitcoin requirement unsatisfied — unconfirmed on a live server.
- The user did nothing wrong and nothing about their server is misconfigured. This is a package from elsewhere presenting itself as a flavor of Bitcoin, and StartOS taking that declaration at face value.
- Start9 is in contact with the registry's operator about changing the package ID so that it presents as a separate stack rather than a flavor of Bitcoin. What has changed so far is the satisfies list, not the ID or the flavor, so this remains live. The same registry carries Fulcrum (BLAKE2b), Datum Gateway, Canary and Mempool Guide for the same chain.

Known since 2026-09-03.
