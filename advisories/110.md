# StartOS outbound connections and OS updates stall for minutes on IPv6-broken networks — fix ships in 0.4.0.2

## Symptom

Outbound connections from the server — including OS updates from the registry — hang for minutes before completing or failing, with no error naming a cause. An OS update download can sit at 0 bytes for several minutes before suddenly proceeding at full speed. This happens on networks where the router advertises an IPv6 default route but does not actually hand the server a usable IPv6 address (SLAAC disabled, no DHCPv6 lease) — a common router/ISP configuration, not an unusual one.

## Affects

Any StartOS server on a LAN or connection whose router advertises IPv6 (a default route, possibly with on-link prefixes) but does not assign the server a global or ULA IPv6 address of its own — including many ISPs with partially-broken IPv6. Does not affect networks with working IPv6, or networks with IPv6 fully disabled at the router.

## Cause

Two defects combined. StartOS treated an interface as IPv6-capable whenever NetworkManager reported an IPv6 gateway, even with no address to send from — so outbound IPv6 packets left with the wrong source address and were silently discarded upstream, hanging until the kernel gave up. Separately, `startd`'s internal SOCKS proxy tried a domain's resolved addresses one at a time with no timeout, so a destination with dead IPv6 addresses ahead of a working IPv4 one could take minutes per dead address before falling back.

## Remedy

Fixed in StartOS 0.4.0.2 (next release). Update when it is available; no workaround is needed in the meantime beyond expecting slow outbound connections and OS update downloads on affected networks.

## Notes

The same change also removes an unrelated log-spam defect (a route-table mirroring routine flooding the OS log with `ip route` usage errors on multi-gateway IPv6 setups) — customers who noticed excessive OS log volume with no other symptom were hitting this too, and it resolves with the same update.
