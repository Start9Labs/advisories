# Coturn: relay-to-relay calls degrade or drop between two clients on the same server — fixed in 4.18.0:1

## Symptom

Calls or connections that must relay through Coturn for both peers (e.g. two people behind symmetric NAT on the same call) fall back to a worse path or cut out. Coturn's logs show repeated entries like:

```
ERROR session 002000000000000006: A peer IP 10.0.[redacted] denied in the range: 10.0.[redacted]-10.255.[redacted] in server 2
```

occurring in the exact seconds of ICE negotiation.

## Affects

Every StartOS Coturn instance with `external-ip` set (i.e. a public IPv4 configured), on versions before 4.18.0:1 — services on StartOS always sit on a `10.0.3.x` container address, so this is hit whenever two clients relaying through the same Coturn need to reach each other's relay candidate. IPv6 relay candidates are not covered by the fix. There is no configuration change that avoids it, since `turnserver.conf` is regenerated on every start.

## Cause

Coturn's two-way `external-ip` mapping rewrites the peer address in a `CreatePermission` request from the public IP back to the container's own private address before checking it against the denied-peer range that this package adds to block LAN access — so the container's own relay address gets caught by its own denylist.

## Remedy

Update to Coturn 4.18.0:1, which adds an explicit `allowed-peer-ip` entry for Coturn's own container address so relay-to-relay permissions are granted while LAN and other-container addresses stay denied. No other action is needed after updating.

## Notes

Fix is IPv4 only — Coturn refuses unique-local peers ahead of the allowed-peer list, so an IPv6 relay candidate cannot be rescued this way; this is a known, undocumented-workaround limitation, not a regression. Verified that the channel-bind permission succeeds after the fix; actual relayed data throughput in this exact scenario was not separately verified by the author, though there is no reason to expect a further issue there.
