# StartOS restores or package installs from backup-fs run extremely slowly — fix merged, arriving in a future update

## Symptom

Restoring a service from backup, or installing/unpacking a package (s9pk) stored on a backup-fs-backed target, takes far longer than expected — tens of minutes for what should be a few seconds, especially over a network share (SMB/NAS). There is no error; the operation eventually completes, but throughput is very slow and the backing storage shows far more data read than the package or backup actually contains.

## Affects

Anyone restoring a service or installing a package from a backup-fs-backed backup target (internal drive, USB disk, or Network Folder) on an affected StartOS build. Worse over network-attached storage, where the extra reads compound with network latency; on fast local NVMe it is still measurably slower but less noticeable.

## Cause

`backup-fs` decodes an entire 1 MiB block for every read, however small, and did not cache the decoded result. Package unpacking during install/restore reads in small units, so a single block was re-fetched and re-decoded many times over — up to roughly 155× the actual data size in the worst case.

## Remedy

A fix has merged that caches the decoded block so each is fetched and decoded once; it is not yet in a released version. Once it ships, restores and installs from backup-fs targets return to normal speed. Until then, expect restores and installs from backup-fs-backed targets — especially over a NAS or Network Folder — to be slow, and avoid interrupting them.

## Notes

The same fix also resolves a related defect where a certain sparse write-then-read pattern in backup-fs could panic and hang the mount; this is not something a customer would trigger directly, but is bundled in the same upcoming fix.
