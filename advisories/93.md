# StartTunnel 1.2.1 — new port forwards fail with "no WAN IP available" on a NAT'd VPS after upgrade

## Symptom

On a cloud VPS behind 1:1 NAT (public IPv4 assigned at the provider edge, not bound to any local interface — the typical AWS, Oracle, GCP or Azure setup), adding a new port forward after upgrading to StartTunnel 1.2.1 fails with:

```
Network Error: no WAN IP available for device 10.59.[redacted]
```

in the CLI, and

```
RPC ERROR: Network Error no WAN IP available for device 10.59.[redacted]
```

in the web UI's Add published port dialog. Port forwards that already existed before the upgrade keep working; only new ones fail. Attempting to fix it with `subnet ... set-wan` fails to parse (`error: the following required arguments were not provided: <SUBNET>`, or `Serialization Error: duplicate key: subnet` if given twice).

## Affects

StartTunnel 1.2.1 on a host whose public IPv4 is not present on any local network interface (1:1-NAT cloud VPS). Not seen on hosts where the public IP is bound directly to the NIC. Existing, pre-upgrade port forwards are unaffected; only adding new ones is blocked.

## Cause

The 1.2.1 upgrade migration did not backfill the new `wanIp` field for subnets and devices that predate it, leaving it `null` even though a usable local address is discoverable. The `subnet ... set-wan` CLI command additionally has a broken argument parser (duplicate `<SUBNET>` positional) that makes it uninvokable in any form.

## Remedy

Use `device set-wan` instead of `subnet ... set-wan` to set the WAN IP directly on the device — this command takes a different argument path that avoids the parser bug, and accepts an address that is not globally routable (e.g. the private interface address), which is what a 1:1-NAT or behind-a-router install needs. This unblocks `port-forward add` immediately, with no upgrade required.

The CLI parsing fix has merged for the next StartTunnel release (1.2.2); update once that ships. A further fix to the underlying WAN-IP model is planned for a later StartTunnel release.

## Do not

- Do not expect `subnet ... set-wan` to work in the meantime — both single- and double-argument forms fail structurally.
- Do not attempt to hand-edit the database to set `wanIp` — the CLI's patch tool requires an undocumented expression syntax and will reject both a full replacement and a targeted patch with `missing field 'webserver': result does not match database model`.

## Notes

- If the host also relies on an HTTP-01 (`certbot`/`nginx`) ACME authenticator on port 80, be aware the same upgrade removes the old port-80 forward without replacing it; the existing certificate keeps working until its next renewal (~40 days later), at which point renewal will fail unless the port-80 forward is re-added the same way (`device set-wan`, then re-adding the forward).
- This is distinct from advisory 92 (inbound IPv6 to a delegated address hanging) — that affects IPv6 connectivity on any topology; this is IPv4 WAN-IP configuration specific to NAT'd VPS hosts.
