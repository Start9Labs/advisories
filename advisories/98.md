# StartTunnel — a disabled published port silently re-enables itself about 30 minutes later

## Symptom

A published port that was disabled (via `start-tunnel port-forward set-enabled --enabled false`, or by toggling it off in the web UI's manual forwards table) shows as disabled in the UI, the CLI and the database — but is still, or again, reachable from the outside. This happens roughly 30–33 minutes after disabling it, once the device using that port next renews its lease. Restarting the StartTunnel daemon makes it go dark again (a restart honours the disabled flag), so the same forward can flip between live and dead depending on whether a restart or a device refresh happened most recently.

## Affects

Anyone running StartTunnel 1.3.0 (current release) who disables a published port while the device on the other end keeps using it — most commonly a manually-added forward that shares the exact external port a service or device already maps (e.g. a hand-added `9735 → <device>:9735` next to a service that maps `9735` itself), and SNI-based hostname or fallback forwards. A port disabled and then never refreshed again (device offline, or the mapping torn down) is not affected.

## Cause

Three of the re-assert code paths (automatic/manual DNAT re-installation, SNI route persistence, SNI fallback persistence) never check the stored `enabled` flag before putting the forward back into the dataplane on a device's periodic PCP/UPnP lease renewal. Only the startup restore path correctly skips disabled entries, which is why a daemon restart re-applies the disable.

## Remedy

There is no released fix yet. To keep a port down, restart the StartTunnel daemon shortly after disabling it, and if it becomes reachable again later, disable it again and restart once more. Watch for this specifically when a disabled forward shares its external port with a device or service that is still actively renewing its mapping.

## Do not

- Assume the UI/CLI showing "disabled" means the port is actually closed — check reachability directly if it matters.

## Notes

Reported and validated by two Start9 engineers against StartTunnel 1.3.0 / master @ `6261b81f6`, found by code review rather than a field report; no fix has merged as of this writing. No customer log or error is produced on either the disable or the re-assert, so there is nothing to grep for — the only tell is the port being reachable when it should not be.
