# Raspberry Pi: root filesystem stays tiny (near-full) even though the partition is much larger

## Symptom

On a Raspberry Pi running StartOS, the server behaves as if disk space is nearly exhausted — installs, updates or backups can fail for lack of room — even though the SD card is much larger than what's in use. Checking with `btrfs filesystem usage` (not `df`, which doesn't show this) reveals the root filesystem itself is only a few GiB, with tens of MiB free, while the partition underneath it is much larger. Growing the filesystem manually (`btrfs filesystem resize max`) against `/media/startos/config` succeeds and frees the space; the same command against `/media/startos/root` fails with `Read-only file system`.

## Affects

Every Raspberry Pi StartOS image (raspberrypi build) from 0.4.0-alpha.21 onward. The first-boot partition resize works normally; only the filesystem inside it stays at its flashed size — the image is built with only squashfs size + 256 MB of slack, so a Pi never gets more free space than that. Not an issue on x86_64 or other aarch64 hardware.

## Cause

First boot's `init_resize.sh` issues the btrfs resize against a read-only bind mount, so the resize ioctl fails; the script does not check the command's exit status, logs success anyway, and removes its own retry hook — so the filesystem never grows on any subsequent boot either.

## Remedy

Fixed in StartOS 0.4.0.2, which corrects `init_resize.sh` to resize through the correct (writable) mount and to fail and retry if the resize does not succeed. Until then, the filesystem can be grown by hand by resizing `/media/startos/config` directly, which is the same underlying filesystem.

## Notes

Found by reading code, then matched to an independent field report of a 1.52 GiB filesystem on a 13.8 GiB partition with about 48 MiB free. Worth flagging to a human: an OS update writes the new rootfs image alongside the running one in `images/`, which may not fit in the space affected Pi boxes have — unconfirmed, not yet tested.
