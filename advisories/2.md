# Core Lightning 26.6.7:1 and earlier do not have the v26.06.7 security fixes, even though the node reports v26.06.7 — update to 26.6.7:2

## Symptom

**Every Core Lightning version before 26.6.7:2 is missing the upstream security fixes. Update to 26.6.7:2.**

This includes 26.6.7:0 and 26.6.7:1, which were published as the security update and are not. A node running either reports `v26.06.7` on startup and does not have the fixes. Checking the version in the interface or the logs will not reveal this — only the StartOS package version does, and it must read **26.6.7:2**.

## Affects

Every Core Lightning package version before 26.6.7:2, including 26.6.7:0 and 26.6.7:1, which were published as the security update, and 26.6.6:13, which runs deliberately offline.

## Cause

The cause is upstream: the Docker images published for Core Lightning v26.06.7 were built by their CI from the wrong source tree and omit the release's security fixes, while still reporting the new version. The Core Lightning developers have confirmed this on their release page. 26.6.7:0 and 26.6.7:1 were built from one of those images. 26.6.7:2 is built from the signed release tarballs instead, which are verified against the developers' own signature at build time.

## Remedy

What to tell a user, by the version they are on:

- **26.6.7:0 or 26.6.7:1** — the node is on the network and unprotected, and was told otherwise. Update to 26.6.7:2. This is the most important case, because nothing about the node's behaviour looks wrong.
- **26.6.6:13** — the node is deliberately offline and unprotected. It accepts no incoming connections, does not reconnect to peers, and cannot send, receive, or forward payments. Updating to 26.6.7:2 protects it and returns it to the network.
- **26.6.6:12 or earlier** — the node is on the network and unprotected. Update to 26.6.7:2.

In every case the answer is the same: update to 26.6.7:2. No configuration changes, nothing to re-enable.

## Notes

Two things updating does not undo, both specific to nodes that spent time on 26.6.6:13:

- If a channel had an in-flight HTLC that expired while the node was offline, the peer may have force-closed that channel. The funds are recovered on-chain by the normal close process, but the channel is gone and has to be reopened. Worth checking for unexpected closures.
- The Core Lightning web interface logged repeated WebSocket connection failures during that period. Offline mode suppressed every port binding, including the websocket that interface uses. This resolves on update and was never a fault in the interface itself.

Dependent services — BTCPay Server, LNbits, Alby Hub, Ride The Lightning, Mempool — reach Core Lightning normally throughout. While the node was offline they saw it with no peers, which can look like those services are the ones that are broken.

Known since 2026-08-27.
